# MVP：从 0→1 完成

## 发布结论

《secret dictator》已经完成首个可玩产品闭环：5–10 名玩家可以从创建或加入房间开始，在没有额外主持人的情况下完成标准对局并进入终局复盘；单个用户也可以通过正式单人模式手动完成完整流程。

本记录用于确认“已经交付什么”。后续开发从稳定性、体验、可观测性和扩展能力继续演进，不再重复执行旧 P0 建设清单。

## 已交付范围

- 本地用户资料、房间临时头像和创建用户后的原意图回跳。
- 普通房间创建、房号/分享加入、准备、退出、房主转移、房间设置和空席认领。
- 单人模式房间、虚拟席位补齐、统一准备、席位视角切换和完整手动对局。
- 5–10 人身份分配、政策牌初始化和私密身份展示。
- 提名、投票、流票、三连败、立法、否决、总统权力和全部标准胜负判定。
- 对局公共桌面、个人待办、政策轨、选举计数器、牌堆数量、身份页和规则页。
- 公开票型、局内历史、结果快照、全部身份公开和关键事件复盘。
- 会话恢复、页面超时处理、快照缓存、实时信号通知、监听退避和轮询降级。
- 写操作幂等、游戏版本冲突、服务端鉴权、公开/私密投影和过期资源清理。

## 架构结果

MVP 最终落地为原生微信小程序和四个 JavaScript 云函数：

- `bootstrapService`：会话和恢复；
- `roomService`：大厅和单人模式；
- `gameService`：状态机、快照、命令和结果；
- `maintenanceService`：初始化与清理。

`game_core` 保存完整真相，公共与个人私密快照分别投影；客户端监听无敏感内容的 `room_sync_signals`，版本变化后通过云函数读取快照，监听失败时回退轮询。

当前架构与接口分别以 [`../architecture.md`](../architecture.md) 和 [`../api.md`](../api.md) 为准。

## 已知工程债

以下事项不否定 MVP 功能闭环，但应作为 1→100 的质量建设候选：

- 自动化测试主要使用本地 stub/mock；真实云函数、数据库权限和云存储仍需目标云环境集成验证。
- 微信开发者工具中的普通多人和单人完整冒烟流程尚未形成可重复的自动化矩阵。
- `room_sync_signals` 自定义安全规则属于云环境配置，需要发布检查确保成员只读和客户端禁写。
- 云资源优化已经从持续轮询演进为实时信号加轮询降级，但各 action 的真实读写占比仍需长期监控。
- 文档与 action/枚举的漂移检查尚未自动化。

这些事项统一进入 [`../roadmap.md`](../roadmap.md)，不继续保留在 MVP 待办清单中。
