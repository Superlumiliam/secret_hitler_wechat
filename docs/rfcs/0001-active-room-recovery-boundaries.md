# RFC-0001：活跃房间恢复与显式清除边界

## 目标

在页面栈重建和小程序运行环境回收后恢复仍有效的大厅或对局，同时保证用户显式返回首页、页面超时或主动退出产生的清除不会被成员扫描撤销。

## 背景与证据

恢复链路以 `user_profiles` 锚点为首选，并在锚点缺失或失效时从唯一有效的 `active` 成员记录自愈。若 `clearActiveRoom` 只把锚点字段设为 `null`，仍为 `active` 的成员会在下一次恢复中重新写回同一锚点，导致显式清除失效。无候选是普通启动状态，不应持续输出诊断日志。

当前接口见 [`../api.md`](../api.md)，恢复数据流见 [`../architecture.md`](../architecture.md)。

## 方案

- `clearActiveRoom` 清空 `activeRoomId` 和 `activeMemberId` 时，将现有内部字段 `activeRoomStatus` 写为 `recovery_suppressed`，表示本次缺锚来自显式清除。
- 锚点自愈遇到 `recovery_suppressed` 时直接返回空，不扫描成员。后续创建、加入或状态迁移写入新的有效锚点时，会用真实房间状态覆盖该标记。
- 因锚点损坏而进行的内部条件清理仍把 `activeRoomStatus` 置空，随后允许按唯一合法候选自愈。
- 成员扫描继续只接受真实、`active`、未过期且状态为 `lobby` 或 `in_game` 的唯一候选。
- 既有锚点的在线刷新和缺失锚点的自愈写入都在事务中重读资料；锚点已变化或出现 `recovery_suppressed` 时放弃写入，并向当前恢复请求返回空房间。
- 零候选不记录日志；多候选和事务重检失败保留诊断日志。

## 边界

- 包含：结果页返回首页、页面超时、旧客户端空 payload 清除、锚点损坏自愈和冷启动恢复。
- 不包含：改变 `leaveRoom` 的成员状态迁移、迁移历史数据、从结束房间反查结果页。
- 必须保持的不变量：主动退出的 `offline` 或 `left` 成员不可自愈；有效的既有结果锚点仍可恢复；旧房间的延迟条件清除不得覆盖新房间锚点。

## 接口与兼容性

`bootstrapService.clearActiveRoom` 继续接受 `{ roomId? }` 并保持响应结构不变。空 payload 继续无条件清除当前锚点。`recovery_suppressed` 只存储在服务端资料中，不进入 `ActiveRoomSummary`，不新增数据库字段或客户端枚举。

## 失败场景与安全

- 带 `roomId` 的清除在事务中核对当前锚点；不匹配时成功返回但不写入抑制标记。
- 清除后即使旧成员仍为 `active`，后续恢复也返回空，直到新的创建或加入写入锚点。
- 清除与恢复交错时，共享的资料事务冲突域保证最终写入重新检查抑制标记；清除先提交后，进行中的恢复不得写回锚点或返回陈旧房间。
- 自愈和在线刷新写入前均在事务中重读资料、房间和成员，避免覆盖并发产生的新锚点。
- 事务前置条件不满足时返回空房间；事务执行异常不得伪装成空恢复，必须沿统一协议返回可重试的 `INTERNAL_ERROR`。
- 不改变 openid 鉴权、成员状态、房间人数、房主迁移或业务命令幂等语义。

## 验收

- [x] 有效大厅或对局执行 `clearActiveRoom` 后再次恢复仍返回 `activeRoom: null`。
- [x] 缺失或损坏锚点仍可从唯一合法候选修复。
- [x] 条件清除房间 A 不影响后来写入的房间 B。
- [x] 清除先于进行中恢复的最终写入提交时，锚点保持抑制且恢复返回空。
- [x] 在线刷新事务异常返回可重试失败，重试后仍能恢复原有效房间。
- [x] 零候选不输出诊断日志，多候选和事务重检失败仍可观察。
- [x] 全部前后端测试、JavaScript 语法检查和 `git diff --check` 通过。
- [x] 无需新增微信开发者工具手工验证；部署后可通过目标云函数日志确认异常诊断。
- [x] 同步更新 `api.md` 和 `architecture.md`；产品、规则和路线图无变化。
