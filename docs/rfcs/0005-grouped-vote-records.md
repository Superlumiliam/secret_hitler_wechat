# RFC-0005：投票记录按票型分组

## 目标

将选举结果弹窗、局内历史和终局复盘中的逐玩家票型格子，统一改为“赞同 / 反对”两组席位名单；同时让公开快照、公开历史与结果快照使用同一分组数据结构。

## 背景与证据

当前公开投票通过 `{ memberId, vote }[]` 下发，三个页面再逐玩家渲染 JA / NEIN 卡片或勾叉格子。该形式在 5–10 人局中信息分散、占用空间大，不利于快速比较两类票型。

## 方案

- 公开投票统一使用：

  ```js
  voteGroups: {
    jaMemberIds: ["mem_1", "mem_2"],
    neinMemberIds: ["mem_3", "mem_4"]
  }
  ```

- 两个数组按席位升序生成，互斥且并集等于本轮全部存活投票玩家；票数由数组长度计算。
- 进行中的未揭示投票仍保存在 `game_core.phaseData.votesByMemberId`，避免改变保密、幂等和重复提交边界。
- 历史页未揭示时只显示提交人数，不列出玩家或票型；揭示后显示两组席位名单。

## 边界

- 包含：选举结果弹窗、局内历史、终局时间线、公开快照、公开事件和结果快照。
- 不包含：投票提交命令、个人私密投票、投票规则、身份或阵营逻辑。
- 必须保持的不变量：最后一票前不公开任何票型；只有存活玩家参与投票；平票仍视为政府未通过。

## 接口与兼容性

- `GameSnapshot.publicState` 删除 `revealedVotes`。
- `voteResult` 增加 `voteGroups`。
- `history.rounds[]` 删除逐玩家 `votes`，增加 `voteGroups`；投票摘要增加提交进度。
- `VOTES_REVEALED` 和 `ResultSnapshot.timeline[]` 用 `voteGroups` 替换 `votes`。
- `SUBMIT_VOTE`、`privateState.voting.myVote` 和枚举不变。
- 不兼容旧房间投票记录或旧客户端，不提供双写、迁移或读取回退。

## 失败场景与安全

- 服务端只在全部存活玩家提交后构造 `voteGroups`。
- 分组数组由服务端真相生成，客户端只负责按公开席位映射文案。
- 命令幂等继续使用逐玩家命令元数据；本变更不改变并发与版本校验。
- 前后端需同步发布，发布后只验证新建房间。

## 验收

- [x] 分票、全票赞同、全票反对均生成完整且有序的分组。
- [x] 未揭示阶段不输出分组票型，只输出提交进度。
- [x] 三个页面统一显示两行分组，空分组显示“无”，10 人名单可换行。
- [x] 旧 `votes` 和 `revealedVotes` 不再出现在公开 DTO。
- [x] 后端与前端自动化测试全部通过。
- [ ] 在微信开发者工具中使用新房间完成 5 人与 10 人视觉验证。
- [x] 同步更新 `api.md`、`architecture.md` 与路线图。

## 决策

方案于 2026-07-29 经需求确认并完成实现；无需 ADR。自动化验收已通过，微信开发者工具视觉验证因当前窗口没有可直接观察的模拟器对局而保留为手工项。
