# RFC-0006：历史轮次档案卡布局

## 目标

参考 `reference/09-历史记录页.png` 的视觉基调重做局内历史的每轮面板，在保留顶部全局统计的前提下，用“第 X 轮提名、政府结果、总统、总理、赞同、反对”档案卡快速呈现每轮选举。

## 背景与证据

现有轮次面板使用圆形轮次章、提名句子、投票摘要和整行名单，信息层级与参考图差异较大；政府通过状态还会被后续立法或总统权力结果覆盖，无法稳定显示在卡片顶部。

## 方案

- 每轮卡片顶部显示“第 X 轮提名”；投票未揭示时不显示结果。
- 政府通过显示“政府通过”；未通过显示“政府未通过 X/3”，其中第三次失败即使随后触发混乱政策也保留 `3/3`。
- 正文固定为总统、总理、赞同、反对四行；标签和席位均使用独立卡片，席位文案为“1号”。
- 总统尚未确定时总统行不显示席位卡；未提名时总理行不显示席位卡；未揭示时赞同、反对行不显示席位卡；已揭示但分组为空时显示“无”卡片。
- 顶部已进行轮次、两类政策数和选举计数器全局面板保持不变。
- 本 RFC 只替代 RFC-0005 中“历史页未揭示时显示提交人数”的页面行为；底层提交进度字段和其他两个投票展示页面不变。

## 边界

- 包含：历史轮次公共摘要与局内历史页。
- 不包含：选举结果弹窗、终局时间线、投票规则和状态机。
- 必须保持：票型揭示前不泄露选择；席位按编号升序展示。

## 接口与兼容性

`history.rounds[].voteSummary` 增加：

- `passed: boolean | null`
- `electionTrackerCount: number`

无新增 action、枚举或错误码；不兼容旧房间历史投影。

## 失败场景与安全

- `passed` 和失败次数只由服务端已公开的 `VOTES_REVEALED` 事件生成。
- 失败次数使用揭示前计数器加一并封顶为 3，不受混乱政策随后归零影响。
- 未揭示轮次固定返回 `passed: null`、`electionTrackerCount: 0`。

## 验收

- [x] 顶部全局统计面板保持原有四项。
- [x] 已通过、普通未通过和第三次未通过显示正确结果。
- [x] 总统、总理与两组票型使用独立席位卡，席位文案不含“玩家”。
- [x] 总统未确定、总理未提名和票型未揭示时不生成对应玩家卡。
- [x] 后端与前端自动化测试通过。
- [ ] 在微信开发者工具中使用真实历史快照完成视觉验证。
- [x] 同步更新产品、API 和路线图文档。

## 决策

方案于 2026-07-29 根据页面参考图和需求细节完成实现，后续需求确认在总理上方增加总统行；无需 ADR。微信开发者工具服务端口关闭，模拟器视觉验证保留为手工项。
