# 《secret hitler》开发者调试模式方案

## 1. 文档目标

本文档定义开发者调试模式的产品边界、能力范围、生产隔离、前后端职责与验收方式。

开发者调试模式只服务于个人开发、联调和手动验收，不是正式玩家功能。它的目标是让开发者在不组织 `5-10` 名真实玩家的情况下，仍能亲自确认一整局游戏的页面表现、私密信息、操作权限、状态推进和异常提示。

## 2. 核心结论

本项目采用“开发者房间 + 虚拟席位 + 本地席位视角切换”的调试方案。

开发者不直接跳过规则，也不通过脚本自动完成整局游戏，而是在开发者房间中创建若干虚拟玩家，并手动切换到不同席位执行对应玩家的合法操作。

第一阶段只实现最短闭环：

- 创建开发者房间。
- 一键补齐虚拟玩家到合法人数。
- 设置全员准备并开局。
- 以指定席位读取快照和查看身份。
- 以指定席位完成提名、投票、立法等合法命令。
- 手动跑完一整局并进入结果页。

该方案必须满足：

- 真实状态机仍然是唯一裁判。
- 快照投影仍然是前端唯一数据来源。
- 私密信息仍然按席位权限下发。
- 调试能力只在开发环境可用。
- 生产环境不能接受任何调试 action 或调试命令。
- 场景种子、全知审计面板、复杂复盘日志都不进入第一阶段。

## 3. 非目标

开发者调试模式不做以下事情：

- 不提供正式玩家可见的机器人玩法。
- 不提供线上人机对战。
- 不实现自动决策 AI。
- 不用脚本自动跑完整局替代人工确认。
- 不允许房主在正式对局中查看或操控其他玩家。
- 不改变标准《secret hitler》规则流程。
- 第一阶段不做场景种子。
- 第一阶段不做身份总览、包含牌序或构成的牌堆摘要等全知审计面板；正式对局桌面展示抽牌堆 / 弃牌堆张数不属于调试审计面板。
- 第一阶段不做复杂复盘日志，只依赖现有结果页与必要的错误提示完成手动验收。

## 4. 开发者房间

开发者房间是带有显式模式标记的特殊房间：

```ts
type RoomMode = 'normal' | 'dev';
```

约束：

- 普通房间固定为 `mode: 'normal'`。
- 开发者房间固定为 `mode: 'dev'`。
- 所有调试能力都必须校验 `mode === 'dev'`。
- 开发者房间只能在开发云环境创建。
- 开发云环境必须用明确 allowlist 判定，例如云函数环境变量 `DEV_CLOUD_ENV_IDS` 或等价配置。
- 后端必须失败关闭：未配置 allowlist、当前云环境不在 allowlist、或无法识别当前环境时，所有 `dev*` action 都返回 `DEV_MODE_DISABLED`。
- 开发者房间的生命周期、房间状态、快照轮询、命令幂等、版本校验仍沿用普通房间机制。

开发者房间的价值是提供可控验收环境，而不是提供第二套游戏规则。

## 5. 虚拟席位

虚拟席位用于模拟真实玩家加入房间。

建议字段：

```ts
interface DevVirtualPlayerMeta {
  isVirtual: true;
  controlledByOpenId: string;
  displayName: string;
  avatarId: string;
}
```

约束：

- 虚拟玩家只允许在开发者房间中存在。
- 第一阶段优先提供“一键补齐虚拟玩家到指定人数”，不要求完整的增删改管理 UI。
- 虚拟玩家在大厅阶段可以通过专用调试 action 设置准备状态。
- 开局后不允许随意添加或删除虚拟玩家，避免破坏已生成的身份、座位、任期限制和事件日志。
- 虚拟玩家在状态机中应尽量表现为普通玩家，只在鉴权层和调试面板中体现差异。
- 虚拟玩家的 `memberId`、座位、存活状态、准备状态、投票状态都应进入正常房间模型。
- 真实开发者自己仍是房主成员。
- 虚拟玩家只写入 `room_members`，不写入 `user_profiles`，不更新真实用户的 `activeRoomId` 或 `activeMemberId`。
- 虚拟玩家准备不复用普通 `setReady` 的 openid 归属逻辑，应提供 `devSetVirtualReady` 或 `devReadyAllVirtualPlayers`。

## 6. 本地席位视角切换

本地席位视角切换是开发者调试模式的核心能力。

开发者可以在调试面板中选择“当前操控席位”，例如：

- 自己
- 虚拟玩家 A
- 虚拟玩家 B
- 虚拟玩家 C

第一阶段不做持久化的 `devSwitchControlledSeat`。前端只在本地保存当前选中的 `controlledMemberId`，并在读取开发者快照和提交游戏命令时显式传给后端。

请求含义：

```ts
interface DevActingMemberPayload {
  roomId: string;
  controlledMemberId?: string;
}
```

- `controlledMemberId` 为空时，表示使用当前真实开发者自己的成员身份。
- `controlledMemberId` 指向虚拟玩家时，表示本次请求模拟该虚拟席位。
- `controlledMemberId` 不写入房间状态，不作为服务端持久偏好。

后端必须统一通过 `resolveActingMember(openId, roomId, controlledMemberId)` 解析行动成员：

1. 先根据 `openId` 和 `roomId` 找到真实开发者自己的房间成员。
2. 如果没有 `controlledMemberId`，返回真实开发者自己的成员。
3. 如果存在 `controlledMemberId`，必须校验房间是 `mode: 'dev'`。
4. 读取该虚拟成员，校验 `isVirtual === true`。
5. 校验该虚拟成员的 `controlledByOpenId === openId`。
6. 校验通过后，返回该虚拟成员作为本次读取快照或提交命令的行动成员。

约束：

- 席位视角切换只允许控制当前开发者创建或持有控制权的虚拟玩家。
- 切换席位不是“获得全知权限”，而是“模拟该玩家正在使用自己的手机”。
- 当前操控席位只能提交该席位在当前阶段合法的命令。
- 非当前行动人、旧版本命令、死者行动等异常仍必须由后端拒绝。
- 普通接口中原本“只按 openid 找成员”的逻辑不能直接用于开发者虚拟席位，必须经过 `resolveActingMember`。

## 7. 第一阶段调试控制条

第一阶段只需要轻量调试控制条，不做全知审计面板。

建议展示：

- 当前房间模式。
- 当前操控席位。
- 可切换的席位列表。
- 当前游戏阶段、版本号、当前行动人。
- 当前席位是否有待办操作。

第一阶段不展示：

- 全部玩家身份总览。
- 包含牌序或构成的牌堆摘要。
- 复杂事件日志。
- 状态注入入口。

这些能力可作为后续扩展，但不阻塞最短闭环。

## 8. 后续扩展能力

以下能力有价值，但不进入第一阶段：

- 场景种子。
- 指定自己或某个虚拟玩家身份。
- 指定独裁者所在席位。
- 指定政策牌堆随机种子。
- 指定开局后第一个总统候选人。
- 身份总览。
- 包含牌序或构成的牌堆摘要。
- 复杂事件日志。
- 直接构造接近特定权力阶段的房间。
- 构造否决权阶段。
- 构造独裁者当选即时胜利场景。
- 构造处决独裁者胜利场景。

约束：

- 后续扩展也必须只在开发者房间和开发云环境中可用。
- 场景种子如后续实现，只能影响开发者房间创建或开局初始化。
- 中途强制改状态如确有需要，应作为更高风险的“状态注入”能力单独设计，不纳入 MVP 调试模式。

## 9. 允许的调试操作

大厅阶段允许：

- 创建开发者房间。
- 一键补齐虚拟玩家到指定人数。
- 设置全部虚拟玩家准备，或设置指定虚拟玩家准备。
- 开始游戏。

对局阶段允许：

- 切换当前操控席位。
- 以当前操控席位提交合法游戏命令。
- 查看第一阶段调试控制条。
- 拉取最新公共快照和当前席位私密快照。
- 在卡死或异常时强制结束开发者房间。

结果阶段允许：

- 查看正常结果页。
- 返回首页或创建新的开发者房间。

## 10. 禁止的调试操作

开发者调试模式禁止：

- 在生产环境创建开发者房间。
- 在普通房间添加虚拟玩家。
- 在普通房间切换席位视角。
- 通过前端传入任意 `memberId` 绕过后端鉴权。
- 绕过 `expectedVersion` 直接推进游戏。
- 绕过状态机直接修改胜负、政策轨、身份或牌堆。
- 在正式页面中暴露身份总览、包含牌序或构成的牌堆摘要、调试日志。
- 让调试命令进入正式用户可访问路径。
- 让虚拟玩家写入或覆盖真实用户的 `user_profiles` 活跃房间状态。

## 11. 前端职责

前端负责提供开发者调试入口和调试面板，但不能承担裁判职责。

前端必须做到：

- 使用编译宏或环境配置控制调试入口。
- 生产包不注册调试入口页面，不展示调试面板。
- 在本地保存当前选中的 `controlledMemberId`。
- 当前操控席位变化后，带上 `controlledMemberId` 重新拉取对应快照。
- 所有写操作仍通过服务层调用云函数。
- 游戏内写操作仍携带 `commandId`、`expectedVersion` 和当前本地选中的 `controlledMemberId`。
- 调试面板与正式页面视觉上明确区分。

前端不得：

- 用本地状态伪造游戏推进。
- 直接读取或监听数据库集合。
- 在本地保存完整真相后再自行裁剪。
- 在生产构建中保留可访问的调试路由。
- 把当前操控席位持久化为服务端房间状态。

## 12. 后端职责

后端是开发者调试模式的最终安全边界。

后端必须做到：

- 校验当前云环境是否允许调试能力。
- 使用明确 allowlist 判定开发云环境，失败时返回 `DEV_MODE_DISABLED`。
- 校验房间 `mode === 'dev'`。
- 校验操作者是否拥有对应虚拟玩家控制权。
- 通过 `resolveActingMember(openId, roomId, controlledMemberId)` 统一解析真实成员或虚拟行动成员。
- 保持普通命令鉴权、幂等、版本控制和状态机校验。
- 调试 action 与普通 action 在代码结构上清晰隔离。
- 生产环境对所有调试 action 返回明确拒绝。
- 虚拟玩家只写入 `room_members`，不写入 `user_profiles`。

后端不得：

- 仅依赖前端编译宏保护调试能力。
- 仅信任前端传入的 `memberId` 或 `playerId`。
- 在普通房间接受调试命令。
- 将完整核心状态返回给普通游戏接口。
- 用普通 `setReady` 加额外参数的方式模拟虚拟玩家准备。

## 13. API 设计原则

具体接口在实现前再同步更新 `/docs/front_back_api.md`。

当前阶段只确定原则：

- 普通 API 不应因为开发者调试模式改变既有语义。
- 调试 API 应使用显式命名，例如 `devCreateRoom`、`devFillVirtualPlayers`、`devSetVirtualReady`、`devReadyAllVirtualPlayers`。
- 第一阶段不做 `devSwitchControlledSeat`，席位切换只通过请求里的 `controlledMemberId` 表达。
- 游戏内玩家行为仍优先复用普通 `submitCommand`，但在开发者房间中允许额外携带 `controlledMemberId`。
- 开发者快照读取需要支持 `controlledMemberId`，以返回对应席位的私密快照。
- 调试 action 必须有独立错误码或可明确映射到现有错误码，其中生产禁用固定返回 `DEV_MODE_DISABLED`。

## 14. 数据隔离

建议增加以下最小字段：

```ts
interface Room {
  mode: 'normal' | 'dev';
}

interface RoomMember {
  isVirtual?: boolean;
  controlledByOpenId?: string;
}
```

约束：

- 普通玩家 `isVirtual` 为空或 `false`。
- 虚拟玩家必须记录控制者。
- 虚拟玩家不写 `user_profiles`，也不参与真实用户活跃房间恢复状态。
- 事件日志应记录真实操作者与被模拟席位，便于排障。
- 开发者房间可以缩短过期时间，避免调试数据长期堆积。

## 15. 手动验收清单

第一阶段开发者调试模式至少应支撑以下人工验收：

1. 一人创建 `5-10` 人房间并完成开局。
2. 切换到每个席位查看身份页，确认私密信息只按权限展示。
3. 依次操控不同席位完成提名、投票、总统弃牌、总理立法。
4. 在随机流程中如遇到权力、处决、否决等后续阶段，则按正常流程继续推进，不要求通过场景种子定向构造。
5. 跑完一整局并进入结果页。
6. 验证旧版本命令、重复点击、非当前行动人提交会被拒绝。
7. 验证切后台或刷新后能恢复房间，并由前端恢复本地当前操控席位。
8. 验证生产构建无法访问任何调试入口，生产云环境对 `dev*` action 返回 `DEV_MODE_DISABLED`。

## 16. 实施顺序建议

建议按以下顺序实现：

1. 增加房间 `mode` 与虚拟玩家数据标记。
2. 后端实现 `DEV_CLOUD_ENV_IDS` allowlist、`DEV_MODE_DISABLED` 和调试 action 拒绝策略。
3. 实现 `resolveActingMember(openId, roomId, controlledMemberId)`。
4. 实现开发者房间创建与一键补齐虚拟玩家。
5. 实现 `devSetVirtualReady` 或 `devReadyAllVirtualPlayers`。
6. 实现前端调试入口、本地 `controlledMemberId` 和席位切换控制条。
7. 让开发者快照读取和 `submitCommand` 支持 `controlledMemberId`。
8. 做生产构建与生产云环境拒绝验证。
