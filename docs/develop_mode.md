# 《secret hitler》开发者调试模式方案

## 1. 文档目标

本文档定义开发者调试模式的产品边界、能力范围、生产隔离、前后端职责与验收方式。

开发者调试模式只服务于个人开发、联调和手动验收，不是正式玩家功能。它的目标是让开发者在不组织 `5-10` 名真实玩家的情况下，仍能亲自确认一整局游戏的页面表现、私密信息、操作权限、状态推进和异常提示。

## 2. 核心结论

本项目采用“开发者房间 + 虚拟席位 + 席位视角切换”的调试方案。

开发者不直接跳过规则，也不通过脚本自动完成整局游戏，而是在开发者房间中创建若干虚拟玩家，并手动切换到不同席位执行对应玩家的合法操作。

该方案必须满足：

- 真实状态机仍然是唯一裁判。
- 快照投影仍然是前端唯一数据来源。
- 私密信息仍然按席位权限下发。
- 调试能力只在开发环境可用。
- 生产环境不能接受任何调试 action 或调试命令。

## 3. 非目标

开发者调试模式不做以下事情：

- 不提供正式玩家可见的机器人玩法。
- 不提供线上人机对战。
- 不实现自动决策 AI。
- 不用脚本自动跑完整局替代人工确认。
- 不允许房主在正式对局中查看或操控其他玩家。
- 不改变标准《secret hitler》规则流程。

## 4. 开发者房间

开发者房间是带有显式模式标记的特殊房间：

```ts
type RoomMode = 'normal' | 'dev';
```

约束：

- 普通房间固定为 `mode: 'normal'`。
- 开发者房间固定为 `mode: 'dev'`。
- 所有调试能力都必须校验 `mode === 'dev'`。
- 开发者房间只能在开发云环境创建。
- 开发者房间的生命周期、房间状态、快照轮询、命令幂等、版本校验仍沿用普通房间机制。

开发者房间的价值是提供可控验收环境，而不是提供第二套游戏规则。

## 5. 虚拟席位

虚拟席位用于模拟真实玩家加入房间。

建议字段：

```ts
interface DevVirtualPlayerMeta {
  isVirtual: true;
  controlledByOpenId: string;
  displayName: string;
  avatarId: string;
}
```

约束：

- 虚拟玩家只允许在开发者房间中存在。
- 虚拟玩家在大厅阶段可以添加、删除、改名、切换头像、设置准备状态。
- 开局后不允许随意添加或删除虚拟玩家，避免破坏已生成的身份、座位、任期限制和事件日志。
- 虚拟玩家在状态机中应尽量表现为普通玩家，只在鉴权层和调试面板中体现差异。
- 虚拟玩家的 `memberId`、座位、存活状态、准备状态、投票状态都应进入正常房间模型。

## 6. 席位视角切换

席位视角切换是开发者调试模式的核心能力。

开发者可以在调试面板中选择“当前操控席位”，例如：

- 自己
- 虚拟玩家 A
- 虚拟玩家 B
- 虚拟玩家 C

切换后，前端应以该席位身份读取对应私密快照，并只展示该席位有权看到的信息。

约束：

- 席位视角切换只允许控制当前开发者创建或持有控制权的虚拟玩家。
- 切换席位不是“获得全知权限”，而是“模拟该玩家正在使用自己的手机”。
- 当前操控席位只能提交该席位在当前阶段合法的命令。
- 非当前行动人、旧版本命令、死者行动等异常仍必须由后端拒绝。

## 7. 调试审计面板

调试审计面板用于排障与人工验收，不属于正式游戏 UI。

建议展示：

- 当前房间模式。
- 当前操控席位。
- 全部席位列表与状态。
- 当前游戏阶段、版本号、当前行动人。
- 最近事件日志。
- 各席位待办摘要。
- 可选的身份总览与牌堆摘要。

身份总览与牌堆摘要属于全知信息，必须：

- 只在开发者房间展示。
- 只在开发环境展示。
- 使用明显的“调试信息”视觉标识。
- 不参与正式页面布局和正式用户流程。

## 8. 场景种子

为了稳定复现关键流程，开发者房间应支持有限的场景种子能力。

优先支持：

- 指定人数。
- 指定自己或某个虚拟玩家身份。
- 指定独裁者所在席位。
- 指定政策牌堆随机种子。
- 指定开局后第一个总统候选人。

后续可扩展：

- 直接构造接近特定权力阶段的房间。
- 构造否决权阶段。
- 构造独裁者当选即时胜利场景。
- 构造处决独裁者胜利场景。

约束：

- 场景种子只影响开发者房间创建或开局初始化。
- 场景种子不应在游戏中途随意改写核心状态。
- 中途强制改状态如确有需要，应作为更高风险的“状态注入”能力单独设计，不纳入 MVP 调试模式。

## 9. 允许的调试操作

大厅阶段允许：

- 创建开发者房间。
- 添加虚拟玩家。
- 删除虚拟玩家。
- 修改虚拟玩家昵称和头像。
- 一键补齐到指定人数。
- 设置全部虚拟玩家准备。
- 选择场景种子。
- 开始游戏。

对局阶段允许：

- 切换当前操控席位。
- 以当前操控席位提交合法游戏命令。
- 查看调试审计面板。
- 拉取最新公共快照和当前席位私密快照。
- 在卡死或异常时强制结束开发者房间。

结果阶段允许：

- 查看正常结果页。
- 查看完整事件日志。
- 返回首页或创建新的开发者房间。

## 10. 禁止的调试操作

开发者调试模式禁止：

- 在生产环境创建开发者房间。
- 在普通房间添加虚拟玩家。
- 在普通房间切换席位视角。
- 通过前端传入任意 `memberId` 绕过后端鉴权。
- 绕过 `expectedVersion` 直接推进游戏。
- 绕过状态机直接修改胜负、政策轨、身份或牌堆。
- 在正式页面中暴露身份总览、牌堆摘要、调试日志。
- 让调试命令进入正式用户可访问路径。

## 11. 前端职责

前端负责提供开发者调试入口和调试面板，但不能承担裁判职责。

前端必须做到：

- 使用编译宏或环境配置控制调试入口。
- 生产包不注册调试入口页面，不展示调试面板。
- 当前操控席位变化后重新拉取对应快照。
- 所有写操作仍通过服务层调用云函数。
- 游戏内写操作仍携带 `commandId` 和 `expectedVersion`。
- 调试面板与正式页面视觉上明确区分。

前端不得：

- 用本地状态伪造游戏推进。
- 直接读取或监听数据库集合。
- 在本地保存完整真相后再自行裁剪。
- 在生产构建中保留可访问的调试路由。

## 12. 后端职责

后端是开发者调试模式的最终安全边界。

后端必须做到：

- 校验当前云环境是否允许调试能力。
- 校验房间 `mode === 'dev'`。
- 校验操作者是否拥有对应虚拟玩家控制权。
- 保持普通命令鉴权、幂等、版本控制和状态机校验。
- 调试 action 与普通 action 在代码结构上清晰隔离。
- 生产环境对所有调试 action 返回明确拒绝。

后端不得：

- 仅依赖前端编译宏保护调试能力。
- 仅信任前端传入的 `memberId` 或 `playerId`。
- 在普通房间接受调试命令。
- 将完整核心状态返回给普通游戏接口。

## 13. API 设计原则

具体接口在实现前再同步更新 `/docs/front_back_api.md`。

当前阶段只确定原则：

- 普通 API 不应因为开发者调试模式改变既有语义。
- 调试 API 应使用显式命名，例如 `devCreateRoom`、`devAddVirtualPlayer`、`devSwitchControlledSeat`。
- 游戏内玩家行为仍优先复用普通 `submitCommand`。
- 只有创建虚拟玩家、切换控制席位、读取调试审计信息等能力需要新增调试 action。
- 调试 action 必须有独立错误码或可明确映射到现有错误码。

## 14. 数据隔离

建议增加以下最小字段：

```ts
interface Room {
  mode: 'normal' | 'dev';
}

interface RoomMember {
  isVirtual?: boolean;
  controlledByOpenId?: string;
}
```

约束：

- 普通玩家 `isVirtual` 为空或 `false`。
- 虚拟玩家必须记录控制者。
- 事件日志应记录真实操作者与被模拟席位，便于排障。
- 开发者房间可以缩短过期时间，避免调试数据长期堆积。

## 15. 手动验收清单

开发者调试模式至少应支撑以下人工验收：

1. 一人创建 `5-10` 人房间并完成开局。
2. 查看每个席位的身份页，确认私密信息只按权限展示。
3. 依次操控不同席位完成提名、投票、立法。
4. 验证投票失败与三连败混乱政策。
5. 验证调查、特别选举、预览政策、处决等权力。
6. 验证极权派政策达到条件后独裁者当选即时胜利。
7. 验证处决独裁者后的自由派胜利。
8. 验证否决权阶段。
9. 验证死亡玩家不可继续行动。
10. 验证旧版本命令、重复点击、非当前行动人提交会被拒绝。
11. 验证切后台或刷新后能恢复当前操控席位和快照。
12. 验证生产构建无法访问任何调试入口。

## 16. 实施顺序建议

建议按以下顺序实现：

1. 增加房间 `mode` 与虚拟玩家数据标记。
2. 后端实现开发环境校验与调试 action 拒绝策略。
3. 实现开发者房间创建与虚拟玩家管理。
4. 实现前端调试入口和大厅阶段虚拟席位管理。
5. 实现席位视角切换和私密快照读取。
6. 实现调试审计面板。
7. 增加场景种子。
8. 做生产构建与生产云环境拒绝验证。
