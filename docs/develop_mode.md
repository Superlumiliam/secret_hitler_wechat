# 《secret dictator》单人模式方案

## 1. 文档目标

本文档定义单人模式的产品边界、能力范围、前后端职责、多人模式隔离边界与验收方式。

单人模式用于让一个用户在不组织 `5-10` 名真实玩家的情况下，也能通过虚拟席位和本地席位视角切换手动完成完整游戏流程。开发者模式废除后，单人模式是普通编译下的正式用户入口，不是开发环境专属能力，也不是新增人机对战、自动 AI 或第二套游戏规则。

旧开发者模式的底层实现可以在迁移阶段被复用，但文档、接口契约和长期代码命名应收敛到 `solo` / `solo*`。对外页面文案统一展示为“单人模式”。

## 2. 核心结论

本项目采用“单人模式房间 + 虚拟席位 + 本地席位视角切换”的方案。

用户不直接跳过规则，也不通过脚本自动完成整局游戏，而是在单人模式房间中创建若干虚拟玩家，并手动切换到不同席位执行对应玩家的合法操作。

第一阶段只实现最短闭环：

- 首页提供“单人模式”入口按钮。
- 点击“单人模式”后进入创建房间页选择 `5-10` 人数，不在首页直接选择人数。
- 创建成功后进入单人模式房间大厅。
- 一键补齐虚拟玩家到目标人数。
- 设置全员准备并开局。
- 以指定席位读取快照和查看身份。
- 以指定席位完成提名、投票、立法等合法命令。
- 手动跑完一整局并进入结果页。

该方案必须满足：

- 真实状态机仍然是唯一裁判。
- 快照投影仍然是前端唯一数据来源。
- 私密信息仍然按席位权限下发。
- 大厅页和游戏对局页沿用当前代码实现逻辑，不为单人模式重写一套页面流程。
- 单人模式入口在普通编译中展示，不再通过开发者模式编译宏或云环境 allowlist 隐藏。
- 多人模式和单人模式必须按房间模式隔离：多人模式不得出现填充虚拟玩家、切换操控席位、单人模式控制条等操作。
- 场景种子、全知审计面板、复杂复盘日志都不进入第一阶段。

## 3. 非目标

单人模式不做以下事情：

- 不提供机器人自动决策。
- 不提供线上人机对战。
- 不实现自动主持或自动跑完整局。
- 不允许普通房间房主查看或操控其他玩家。
- 不改变标准《secret dictator》规则流程。
- 不保留开发者模式作为用户或环境概念；旧实现只作为迁移参考。
- 第一阶段不做场景种子。
- 第一阶段不做身份总览、包含牌序或构成的牌堆摘要等全知审计面板；正式对局桌面展示抽牌堆 / 弃牌堆张数不属于调试审计面板。
- 第一阶段不做复杂复盘日志，只依赖现有结果页与必要的错误提示完成手动验收。

## 4. 单人模式房间

单人模式房间是带有显式模式标记的特殊房间。房间模式长期枚举应区分普通多人房间和单人模式房间：

```ts
type RoomMode = 'normal' | 'solo';
```

约束：

- 普通房间固定为 `mode: 'normal'`。
- 单人模式房间固定为 `mode: 'solo'`。
- 所有单人模式专用能力都必须校验 `mode === 'solo'`。
- 单人模式是普通编译下的正式能力，不再需要开发者模式环境 allowlist、开发者编译宏或 `DEV_MODE_DISABLED` 之类的环境拒绝逻辑。
- 单人模式房间的生命周期、房间状态、快照轮询、命令幂等、版本校验仍沿用普通房间机制。

单人模式房间的价值是提供一人完整体验与验收环境，而不是提供第二套游戏规则。

## 5. 首页与创建房间入口

首页入口调整为三个主入口：

- 创建房间
- 加入房间
- 单人模式

入口流程：

1. 用户点击首页“单人模式”。
2. 若无本地用户资料，先跳转创建用户页；保存形象后回到首页，用户重新点击“单人模式”。
3. 若已有本地用户资料，进入创建房间页。
4. 创建房间页沿用当前“创建房间”页面形态，选择 `5-10` 人对局人数。
5. 用户确认后创建 `mode: 'solo'` 的单人模式房间。
6. 创建成功后进入房间大厅页。

要求：

- 首页不直接展示单人模式人数选择。
- 创建房间页需要能根据入口来源区分普通创建和单人模式创建。
- 普通“创建房间”仍创建 `mode: 'normal'` 房间。
- “单人模式”创建成功后的大厅页、对局桌面页、身份页、规则页、历史页、结果页均按当前代码实现逻辑复用。
- 页面中文文案使用“单人模式”，不出现“开发者房间”作为用户可见概念。

## 6. 虚拟席位

虚拟席位用于模拟真实玩家加入房间。

建议字段：

```ts
interface SoloVirtualPlayerMeta {
  isVirtual: true;
  controlledByOpenId: string;
  displayName: string;
  avatarId: string;
}
```

约束：

- 虚拟玩家只允许在单人模式房间中存在。
- 第一阶段优先提供“一键补齐虚拟玩家到指定人数”，不要求完整的增删改管理 UI。
- 虚拟玩家在大厅阶段可以通过专用 action 设置准备状态。
- 开局后不允许随意添加或删除虚拟玩家，避免破坏已生成的身份、座位、任期限制和事件日志。
- 虚拟玩家在状态机中应尽量表现为普通玩家，只在鉴权层和单人模式控制条中体现差异。
- 虚拟玩家的 `memberId`、座位、存活状态、准备状态、投票状态都应进入正常房间模型。
- 真实用户自己仍是房主成员。
- 虚拟玩家只写入 `room_members`，不写入 `user_profiles`，不更新真实用户的 `activeRoomId` 或 `activeMemberId`。
- 虚拟玩家准备不复用普通 `setReady` 的 openid 归属逻辑，应提供 `soloSetVirtualReady` 或 `soloReadyAllVirtualPlayers`。

## 7. 本地席位视角切换

本地席位视角切换是单人模式的核心能力。

用户可以在单人模式控制条中选择“当前操控席位”，例如：

- 自己
- 虚拟玩家 A
- 虚拟玩家 B
- 虚拟玩家 C

第一阶段不做持久化的 `soloSwitchControlledSeat`。前端只在本地保存当前选中的 `controlledMemberId`，并在读取快照和提交游戏命令时显式传给后端。

请求含义：

```ts
interface SoloActingMemberPayload {
  roomId: string;
  controlledMemberId?: string;
}
```

- `controlledMemberId` 为空时，表示使用当前真实用户自己的成员身份。
- `controlledMemberId` 指向虚拟玩家时，表示本次请求模拟该虚拟席位。
- `controlledMemberId` 不写入房间状态，不作为服务端持久偏好。

后端必须统一通过 `resolveActingMember(openId, roomId, controlledMemberId)` 解析行动成员：

1. 先根据 `openId` 和 `roomId` 找到真实用户自己的房间成员。
2. 如果没有 `controlledMemberId`，返回真实用户自己的成员。
3. 如果存在 `controlledMemberId`，必须校验房间是 `mode: 'solo'`。
4. 读取该虚拟成员，校验 `isVirtual === true`。
5. 校验该虚拟成员的 `controlledByOpenId === openId`。
6. 校验通过后，返回该虚拟成员作为本次读取快照或提交命令的行动成员。

约束：

- 席位视角切换只允许控制当前用户创建或持有控制权的虚拟玩家。
- 切换席位不是“获得全知权限”，而是“模拟该玩家正在使用自己的手机”。
- 当前操控席位只能提交该席位在当前阶段合法的命令。
- 非当前行动人、旧版本命令、死者行动等异常仍必须由后端拒绝。
- 普通接口中原本“只按 openid 找成员”的逻辑不能直接用于虚拟席位，必须经过 `resolveActingMember`。

## 8. 第一阶段单人模式控制条

第一阶段只需要轻量单人模式控制条，不做全知审计面板。

建议展示：

- 当前房间模式。
- 当前操控席位。
- 可切换的席位列表。
- 当前游戏阶段、版本号、当前行动人。
- 当前席位是否有待办操作。

第一阶段不展示：

- 全部玩家身份总览。
- 包含牌序或构成的牌堆摘要。
- 复杂事件日志。
- 状态注入入口。

这些能力可作为后续扩展，但不阻塞最短闭环。

## 9. 不纳入单人模式的旧调试能力

以下能力属于旧开发者模式或测试夹具范畴，不纳入面向用户的单人模式产品能力：

- 场景种子。
- 指定自己或某个虚拟玩家身份。
- 指定独裁者所在席位。
- 指定政策牌堆随机种子。
- 指定开局后第一个总统候选人。
- 身份总览。
- 包含牌序或构成的牌堆摘要。
- 复杂事件日志。
- 直接构造接近特定权力阶段的房间。
- 构造否决权阶段。
- 构造独裁者当选即时胜利场景。
- 构造处决独裁者胜利场景。

约束：

- 如果后续确需保留这些能力，应作为内部测试夹具或维护工具单独设计，不挂在普通用户单人模式入口下。
- 单人模式第一阶段只提供按真实规则手动跑完整局所需的虚拟席位、席位切换和合法命令提交能力。
- 中途强制改状态如确有需要，应作为更高风险的“状态注入”能力单独设计，不纳入单人模式。

## 10. 允许的单人模式操作

大厅阶段允许：

- 创建单人模式房间。
- 一键补齐虚拟玩家到指定人数。
- 设置全部虚拟玩家准备，或设置指定虚拟玩家准备。
- 开始游戏。

对局阶段允许：

- 切换当前操控席位。
- 以当前操控席位提交合法游戏命令。
- 查看第一阶段单人模式控制条。
- 拉取最新公共快照和当前席位私密快照。
- 在卡死或异常时强制结束单人模式房间。

结果阶段允许：

- 查看正常结果页。
- 返回首页或创建新的单人模式房间。

## 11. 禁止的单人模式操作

单人模式禁止：

- 在普通房间添加虚拟玩家。
- 在普通房间切换席位视角。
- 通过前端传入任意 `memberId` 绕过后端鉴权。
- 绕过 `expectedVersion` 直接推进游戏。
- 绕过状态机直接修改胜负、政策轨、身份或牌堆。
- 在普通房间页面中暴露身份总览、包含牌序或构成的牌堆摘要、调试日志。
- 让单人模式专用命令进入普通房间路径。
- 让虚拟玩家写入或覆盖真实用户的 `user_profiles` 活跃房间状态。

## 12. 前端职责

前端负责提供单人模式入口和控制条，但不能承担裁判职责。

前端必须做到：

- 首页展示“单人模式”按钮，点击后进入创建房间页选择人数。
- 创建房间页根据入口来源创建普通房间或单人模式房间。
- 普通编译必须展示单人模式入口，不再用开发者模式编译宏隐藏入口。
- 单人模式创建失败时，应按后端错误码提示创建失败，不在前端假定一定可用，也不提示“当前环境不可用”这类旧开发者模式文案。
- 在本地保存当前选中的 `controlledMemberId`。
- 当前操控席位变化后，带上 `controlledMemberId` 重新拉取对应快照。
- 所有写操作仍通过服务层调用云函数。
- 游戏内写操作仍携带 `commandId`、`expectedVersion` 和当前本地选中的 `controlledMemberId`。
- 大厅页和游戏对局页沿用当前代码实现逻辑，只在单人模式房间中增加必要入口或控制条。

前端不得：

- 用本地状态伪造游戏推进。
- 除只读监听当前活跃房间的 `room_sync_signals` 外，直接读取、写入或监听数据库集合；该信号只用于通知版本变化，业务数据仍必须通过云函数快照获取。
- 在本地保存完整真相后再自行裁剪。
- 把当前操控席位持久化为服务端房间状态。
- 为单人模式复制一套独立大厅或独立对局页面。

## 13. 后端职责

后端是单人模式的最终安全边界。

后端必须做到：

- 校验房间 `mode === 'solo'`。
- 校验操作者是否拥有对应虚拟玩家控制权。
- 通过 `resolveActingMember(openId, roomId, controlledMemberId)` 统一解析真实成员或虚拟行动成员。
- 保持普通命令鉴权、幂等、版本控制和状态机校验。
- 单人模式 action 与普通 action 在代码结构上清晰隔离。
- 虚拟玩家只写入 `room_members`，不写入 `user_profiles`。

后端不得：

- 仅依赖前端入口保护单人模式能力。
- 仅信任前端传入的 `memberId` 或 `playerId`。
- 在普通房间接受单人模式命令。
- 将完整核心状态返回给普通游戏接口。
- 用普通 `setReady` 加额外参数的方式模拟虚拟玩家准备。

## 14. API 设计原则

具体接口在实现前再同步更新 `/docs/front_back_api.md`。

当前阶段只确定原则：

- 普通 API 不应因为单人模式改变既有语义。
- 单人模式 API 使用显式 `solo*` 命名，例如 `soloCreateRoom`、`soloFillVirtualPlayers`、`soloSetVirtualReady`、`soloReadyAllVirtualPlayers`。
- 第一阶段不做 `soloSwitchControlledSeat`，席位切换只通过请求里的 `controlledMemberId` 表达。
- 游戏内玩家行为仍优先复用普通 `submitCommand`，但在单人模式房间中允许额外携带 `controlledMemberId`。
- 单人模式快照读取需要支持 `controlledMemberId`，以返回对应席位的私密快照。
- 单人模式 action 必须有独立错误码或可明确映射到现有错误码；错误语义围绕房间模式、权限、状态机与参数校验，不再围绕开发环境可用性。

## 15. 数据隔离

建议增加以下最小字段：

```ts
interface Room {
  mode: 'normal' | 'solo';
}

interface RoomMember {
  isVirtual?: boolean;
  controlledByOpenId?: string;
}
```

约束：

- 普通玩家 `isVirtual` 为空或 `false`。
- 虚拟玩家必须记录控制者。
- 虚拟玩家不写 `user_profiles`，也不参与真实用户活跃房间恢复状态。
- 事件日志应记录真实操作者与被模拟席位，便于排障。
- 单人模式房间可以缩短过期时间，避免数据长期堆积。

## 16. 手动验收清单

第一阶段单人模式至少应支撑以下人工验收：

1. 从首页点击“单人模式”，进入创建房间页选择 `5-10` 人数。
2. 创建单人模式房间后进入大厅页，一键补齐虚拟玩家并完成开局。
3. 大厅页和游戏对局页行为与当前代码实现逻辑一致。
4. 切换到每个席位查看身份页，确认私密信息只按权限展示。
5. 依次操控不同席位完成提名、投票、总统弃牌、总理立法。
6. 在随机流程中如遇到权力、处决、否决等后续阶段，则按正常流程继续推进，不要求通过场景种子定向构造。
7. 跑完一整局并进入结果页。
8. 验证旧版本命令、重复点击、非当前行动人提交会被拒绝。
9. 验证切后台或刷新后能恢复房间，并由前端恢复本地当前操控席位。
10. 验证普通编译可见单人模式入口；正式云环境可创建单人模式房间；普通多人房间拒绝虚拟玩家、席位切换和单人模式控制条。

## 17. 实施顺序建议

建议按以下顺序实现：

1. 保留房间 `mode` 与虚拟玩家数据标记。
2. 调整首页入口，新增“单人模式”按钮。
3. 调整创建房间页入口来源，让普通创建与单人模式创建共用人数选择页面。
4. 后端移除开发者模式环境 allowlist 与 `DEV_MODE_DISABLED` 语义，改为通过 `mode: 'solo'` 隔离单人模式能力。
5. 确认 `resolveActingMember(openId, roomId, controlledMemberId)` 支持真实成员和虚拟行动成员。
6. 确认单人模式房间创建与一键补齐虚拟玩家链路。
7. 确认 `soloSetVirtualReady` 或 `soloReadyAllVirtualPlayers` 可用于大厅准备。
8. 在复用大厅页和对局页的前提下接入本地 `controlledMemberId` 和席位切换控制条。
9. 让单人模式快照读取和 `submitCommand` 支持 `controlledMemberId`。
10. 做普通编译入口可见性、正式云环境可用性与普通多人房间隔离验证。
