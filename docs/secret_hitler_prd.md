# 《揭秘希特勒面杀助手》产品需求文档（PRD）

## 1. 文档目标

本文档用于定义《揭秘希特勒面杀助手》微信小程序的产品边界、核心流程、信息权限、异常处理与非功能要求。

这份 PRD 的定位不是简短需求清单，而是后续以下工作的统一输入：

- 交互与界面设计
- 小程序页面拆分与组件设计
- 云函数 / 数据模型 / 状态机设计
- 联机同步与权限控制设计
- 测试用例与验收标准设计

规则层面的完整说明以 `/docs/game_rules.md` 为准；本文档只保留产品实现所需的规则映射与产品化决策。

## 2. 产品定义

### 2.1 产品名称

揭秘希特勒面杀助手

### 2.2 产品定位

一款服务于线下同桌聚会场景的《揭秘希特勒 / Secret Hitler》微信小程序。  
它的职责不是替代线下社交，而是作为中立、低打扰、可同步的裁判系统，帮助玩家完成：

- 创建房间与组局
- 座位顺序确定
- 私密身份分发
- 每轮流程推进
- 隐藏信息的安全传达
- 胜负判定与本局复盘

### 2.3 目标用户

- 熟人聚会中的桌游玩家
- 希望快速开局、不想人工主持的玩家
- 对《揭秘希特勒》规则不够熟悉的新玩家

### 2.4 使用边界

本产品默认服务于“线下面对面同场游戏”。

本产品负责：

- 游戏流程裁判
- 隐私信息分发
- 公开信息同步
- 规则提示与异常拦截

本产品不负责：

- 线上语音 / 视频通话
- 陌生人匹配
- 长期战绩社区
- AI 主持人发言分析
- 自定义魔改规则编辑器

## 3. 产品愿景与核心价值

### 3.1 产品愿景

让一局《揭秘希特勒》从“找规则、分身份、记流程、怕出错”，变成“扫码进房、系统发牌、按提示推进、专注博弈”。

### 3.2 核心价值

#### 对玩家的价值

- 降低开局门槛，减少手动发牌、夜晚确认、规则解释的负担
- 降低规则出错率，避免漏掉阶段、权力、胜负判定
- 保护隐藏信息，减少线下传卡时的身份泄露风险
- 给新玩家提供阶段化提示，降低学习成本

#### 对后续技术设计的价值

- 游戏流程可建模为明确状态机
- 公开信息与私密信息可拆分投影
- 玩家操作可抽象为可校验命令
- 整局行为可沉淀为事件日志，便于重连、复盘和测试

## 4. 产品原则

### 4.1 中立裁判

系统只做规则执行者，不拥有“房主可偷看所有身份”这类特权。

### 4.2 私密数据只给本人

任何隐藏信息默认只发给合法查看人。身份页只展示当前玩家自己的身份信息，不做额外遮罩、定时隐藏或复杂保密流程。

### 4.3 线下低打扰

玩家大部分时间应专注面对面交流。小程序只在需要确认、投票、选牌、执行权力时打断用户。

### 4.4 规则优先于操作自由

一切关键动作以规则校验为准，客户端不允许跳步、不允许越权、不允许绕开阶段限制。

### 4.5 断线可恢复

玩家临时退到后台、网络抖动、切到聊天界面后，回到小程序应能尽量恢复到自己当前应见的状态。

## 5. 产品目标与非目标

### 5.1 MVP 版本目标

MVP 版本应支持完成一整局标准《揭秘希特勒》游戏，满足以下目标：

- 支持 `5-10` 人标准局
- 支持从创建房间到开始游戏的完整组局流程
- 支持完整官方规则流程推进
- 支持所有隐藏信息的定向安全展示
- 支持玩家断线重进后的状态恢复
- 支持本局结束后的结果回顾与流程复盘
- 对局结束后不要求长期保留历史数据

### 5.2 非目标

以下内容不纳入当前版本：

- 异地联机玩法优化
- 观战模式
- 自定义扩展包 / 自定义规则
- 跨局战绩排名
- 好友关系链、社交动态
- 音频主持、语音播报、语音转写

## 6. 用户角色

### 6.1 房主

房主仅在“组局阶段”拥有轻量管理职责：

- 创建房间
- 分享房间
- 调整或确认座位顺序
- 发起开始游戏

房主在游戏开始后不拥有额外信息权限，不可查看其他玩家身份或牌面。

### 6.2 玩家

玩家是核心角色，负责：

- 加入房间并确认座位
- 查看自己的私密身份信息
- 在自己的行动阶段执行投票、选牌、权力等操作
- 查看公共桌面状态并参与线下讨论

### 6.3 已出局玩家

已出局玩家仍保留房间只读权限，但不可继续参与：

- 投票
- 被提名
- 成为总统候选人
- 执行任何主动操作

### 6.4 系统

系统是隐式角色，负责：

- 保存可信状态
- 下发不同玩家可见的数据
- 执行规则校验
- 推进阶段
- 判定胜负

## 7. 核心使用场景

### 7.1 熟人局快速开场

一名玩家从首页进入创建房间页，选择本局人数并分享房号或小程序转发卡片，其余玩家快速加入。MVP 中系统按加入顺序生成座位顺序，全员准备后由房主开局。

### 7.2 无主持人标准局

所有身份分发、提名、投票、立法、总统权力、胜负判定都由系统引导执行，桌上不需要额外主持人。

### 7.3 局内查看规则

局内允许玩家随时查看游戏规则和游戏流程

### 7.4 中途断线 / 切后台恢复

玩家在切到微信聊天、复制房号、被电话打断后重新回到小程序，仍能恢复自己的身份信息和当前待办操作。

### 7.5 赛后复盘

对局结束后，系统展示身份全公开结果、关键回合与胜负原因，帮助玩家讨论和复盘。

## 8. 范围拆分

### 8.1 P0 必做范围

| 模块 | 说明 |
| --- | --- |
| 房间管理 | 创建房间、加入房间、分享、退出、房间有效期 |
| 玩家准备 | 玩家准备、房主开局、人数合法性校验 |
| 身份分发 | 按人数发放角色、党派、队友信息 |
| 公共桌面 | 展示政策轨、选举轨、当前阶段、当前行动人、存活状态 |
| 流程引擎 | 完整支持选举、立法、总统权力、否决权、胜负判定 |
| 私密行动 | 投票、总统弃牌、总理立法、调查、特别选举、处决 |
| 结果复盘 | 展示最终身份、胜利原因、关键事件时间线 |
| 异常恢复 | 断线重进、重复点击拦截、非法操作拦截 |

### 8.2 P1 可扩展范围

| 模块 | 说明 |
| --- | --- |
| 阶段倒计时 | 为投票、选牌、执行权力提供倒计时能力 |
| 主持提示增强 | 更丰富的新手解释、阶段动画、术语百科 |
| 座位管理 | 按实际线下座位确认顺序，支持房主调整；MVP 开发中不考虑 |
| 房主管理增强 | 在 MVP 自动转移房主基础上，补充更丰富的移交与提示策略 |
| 对局分享图 | 结束后生成可分享的结果卡片 |
| 轻量数据分析 | 汇总平均时长、常见卡点、异常退出率 |

## 9. 关键产品化决策

这些决策会直接影响后续技术架构和数据模型。

### 9.1 线下座位顺序后续显式建模

《揭秘希特勒》依赖顺时针轮换，因此“加入顺序”不能直接等同于“座位顺序”。

MVP 暂不支持房主调整座位，先以玩家加入顺序生成稳定座位顺序；后续 P1 座位管理再支持按实际线下座位调整。

产品要求：

- 玩家加入后先进入房间大厅
- MVP 中座位顺序由加入顺序确定
- 游戏开始后座位顺序锁定，整局不可再改

### 9.2 房主不是裁判权限拥有者

房主仅负责开局组织，游戏内不拥有额外秘密信息查看权。

这意味着架构上不能把“房主客户端”当作可信裁判端。

### 9.3 分享方式以微信小程序能力为准

分享方式应以“小程序转发卡片”或“房号加入”为主，而不是依赖通用网页链接。

要求：

- 分享路径中不能携带任何私密信息
- 房号应便于口头输入和线下传播
- 即使分享卡片失效，也可通过房号加入房间

### 9.4 用户展示名不能依赖微信旧式头像昵称授权

产品应允许玩家使用系统默认昵称或手动输入展示名，不把读取微信完整用户资料作为前置条件。

### 9.5 对局记录默认不长期保留

产品只需要支持“本局进行中”和“刚结束时”的复盘查看，不要求跨天历史战绩查询。

## 10. 术语与规则映射

为避免产品文档和后续技术设计术语不一致，约定以下核心概念：

| 术语 | 含义 |
| --- | --- |
| 房间（Room） | 一次组局容器，承载玩家、座位、对局状态 |
| 对局（Game） | 房间内的一次实际游戏过程 |
| 座位（Seat） | 线下桌面顺序，决定总统轮换方向 |
| 阶段（Phase） | 当前流程状态，如提名、投票、立法、执行权力 |
| 公共信息（Public State） | 所有玩家都能看到的信息 |
| 私密信息（Private State） | 仅特定玩家可见的信息 |
| 系统隐藏信息（System Secret） | 仅系统内部可见的信息，如牌库顺序 |
| 命令（Command） | 由客户端发起、等待服务端校验的操作 |
| 事件（Event） | 经过校验后被确认写入的事实，如“某玩家投了 Ja” |

## 11. 信息可见性设计

隐藏信息桌游的核心不是“把数据存起来”，而是“严格控制谁能看到什么”。

### 11.1 公共信息

所有玩家可见：

- 房间号
- 玩家列表与座位顺序
- 存活 / 出局状态
- 当前总统候选人、总理候选人、当选政府
- 每轮公开投票结果
- 选举轨进度
- 自由派 / 法西斯政策数量
- 当前阶段名称与操作提示
- 已公开发生的总统权力目标
- 游戏结果与胜利原因

### 11.2 玩家私密信息

仅玩家本人可见：

- 自己的角色与党派
- 自己可知的队友信息
- 自己当前待执行的动作
- 自己尚未公开的投票选择
- 自己在总统 / 总理阶段收到的政策牌
- 自己作为总统调查得到的阵营结果
- 自己作为总统预览到的牌顶信息

### 11.3 系统隐藏信息

只能由系统持有：

- 完整角色映射
- 牌库顺序
- 弃牌堆细节
- 尚未公开的立法阶段中间态
- 仅对部分玩家生效的阶段临时数据
- 用于校验重复提交和阶段一致性的内部版本号

### 11.4 权限原则

- 房主看到的内容不应超过普通玩家
- 服务端必须按“玩家视角”生成数据，不允许前端拿到完整状态后自行隐藏
- 所有关键命令都必须再次校验操作者、阶段和目标是否合法

## 12. 房间生命周期与状态机要求

为了便于后续架构设计，产品层面先明确房间与游戏生命周期。

### 12.1 房间生命周期

```mermaid
flowchart LR
  A["首页创建入口"] --> B["创建房间"]
  B --> C["大厅组局"]
  C --> D["锁定人数与座位"]
  D --> E["身份分发"]
  E --> F["游戏进行中"]
  F --> G["结算与复盘"]
  G --> H["房间归档 / 失效"]
```

### 12.2 核心阶段状态

建议后续技术设计至少支持以下阶段状态：

| 阶段 | 说明 | 主要操作者 |
| --- | --- | --- |
| `lobby` | 组局阶段，玩家加入、离开、准备 | 房主 / 全体玩家 |
| `nomination` | 总统候选人提名总理候选人 | 当前总统候选人 |
| `voting` | 全体存活玩家投票 | 全体存活玩家 |
| `hitler_check` | 在 `3+` 法西斯政策后做总理是否希特勒判定 | 系统 |
| `legislative_president` | 总统从 3 张中弃 1 张 | 当前总统 |
| `legislative_chancellor` | 总理从 2 张中定 1 张或申请否决 | 当前总理 |
| `veto_response` | 总统决定是否接受否决 | 当前总统 |
| `executive_action` | 执行调查 / 特别选举 / 预览 / 处决 | 当前总统 |
| `round_result` | 回合收束并准备进入下一轮 | 系统 |
| `game_ended` | 胜负已确定，只读展示 | 系统 / 全体玩家 |

### 12.3 阶段切换要求

- 任一时刻只能有一个主阶段
- 每个阶段必须明确“谁可以操作”
- 阶段切换必须由已确认事件触发，而不是纯前端倒推
- 私密阶段结束前，不应向其他玩家泄露中间过程

## 13. 关键业务流程

### 13.1 组局流程

1. 玩家创建房间，生成房号
2. 其他玩家通过房号或分享卡片进入
3. 玩家进入座位列表，可在房间大厅修改展示名
4. 系统按加入顺序生成座位顺序
5. 全员准备
6. 当人数满足 `5-10` 时，房主点击开始
7. 系统锁定玩家名单与座位顺序，进入身份分发

### 13.2 开局身份流程

1. 系统按人数生成身份组合
2. 系统为每位玩家生成个人私密身份视图
3. 游戏进入对局桌面页
4. 玩家可在对局桌面页点击“我的身份”进入身份页，查看自己的角色、党派和可知队友
5. 玩家点击“我知道了”返回对局桌面页

### 13.3 单回合流程

1. 系统确定当前总统候选人
2. 总统提名总理候选人
3. 全体存活玩家投票
4. 若失败则推进选举轨；若三连败则翻顶牌结算
5. 若通过且已满足“希特勒当选即输”的判定条件，则先做即时胜负判断
6. 若游戏继续，则进入立法阶段
7. 如触发总统权力，则进入对应执行阶段
8. 回合收束，进入下一轮

### 13.4 结束与复盘流程

1. 系统判定胜利阵营与胜利原因
2. 解锁全员身份公开结果
3. 展示关键事件时间线
4. 玩家可在当前房间内查看复盘
5. 房间在一定时间后自动失效

## 14. 功能需求明细

### 14.1 房间管理

#### 目标

支持线下快速组局，并让玩家能够稳定回到同一房间。

#### 功能要求

- 创建房间时生成唯一房号
- 玩家可通过房号加入
- 支持微信转发房间卡片
- 房间大厅显示当前人数、玩家列表、准备状态
- 开局前允许玩家退出房间
- 开局后玩家退出应视为断线，不直接销毁座位

#### 规则与约束

- 房间开始游戏后锁定玩家列表
- 非法人数不得开局
- 房间过期后不能再加入

### 14.2 座位与准备

#### 目标

MVP 先以加入顺序生成系统可计算的顺时针顺序，后续 P1 再支持房主按线下座位调整。

#### 功能要求

- 大厅中必须展示明确的 `1-N` 座位顺序
- MVP 中不提供座位调整能力
- 玩家可确认自己在当前系统顺序中的座位
- 全员准备完成后才能开始游戏

#### 架构输入

- 座位顺序应是独立字段；MVP 可由加入顺序初始化，后续座位调整能力只更新该字段
- 后续总统轮换、特别选举恢复顺序都依赖该字段

### 14.3 身份分发与私密查看

#### 目标

在不泄露身份的前提下，完成规则合法的秘密信息分发。

#### 功能要求

- 按人数自动分配角色组合
- 玩家只能看到自己的角色、党派和允许看到的队友信息
- 身份页不做遮罩、二次点击展示、定时隐藏或特殊保密逻辑
- 玩家可在游戏进行中重新查看自己的身份信息
- 不允许任意玩家查看其他人的身份页

#### 特殊说明

- `5-6` 人局中，希特勒可见普通法西斯
- `7-10` 人局中，希特勒不可见普通法西斯

### 14.4 公共桌面展示

#### 目标

让所有玩家随时知道公共局势和当前该谁行动。

#### 功能要求

- 展示存活玩家座位图
- 高亮当前总统候选人、总理候选人、当选政府
- 展示选举轨、自由派政策轨、法西斯政策轨
- 展示当前阶段名称和简明规则提示
- 展示是否已进入“`3+` 法西斯政策，希特勒当选即输”状态
- 展示否决权是否解锁

### 14.5 提名与投票

#### 目标

让全体玩家以最少操作完成一轮合法选举。

#### 功能要求

- 当前总统候选人只能提名符合规则的目标
- 被禁提名玩家应在界面上明显置灰并给出原因
- 存活玩家必须完成投票后才能揭示结果
- 投票结果一次性公开，不逐个揭示
- 平票按失败处理

#### 交互要求

- 投票提交前应有确认动作，避免误触
- 投票未全部完成前，不显示任何中间票型

### 14.6 立法阶段

#### 目标

安全处理总统与总理的秘密选牌动作。

#### 功能要求

- 总统收到 3 张政策牌，只能弃 1 张
- 总理收到 2 张政策牌，只能颁布 1 张或在允许时发起否决
- 牌面只对当前合法操作者可见
- 立法结果确认后同步更新公共政策轨
- 牌库不足时系统自动完成重洗逻辑

#### 交互要求

- 政策牌默认背面进入，翻开后再选择
- 提交前需二次确认
- 提交后不可撤销

### 14.7 总统权力

#### 目标

将规则中的总统权力转化为明确、可校验、可同步的产品动作。

#### 功能要求

- 根据人数和法西斯政策数量自动决定是否触发权力
- 支持 `调查忠诚`
- 支持 `特别选举`
- 支持 `政策预览`
- 支持 `处决`
- 每种权力都必须校验可选目标是否合法
- 处决目标只要求是存活玩家，允许当前总统选择处决自己

#### 公共同步要求

- 公开谁被调查 / 被特别选举 / 被处决
- 不公开调查结果与政策预览内容
- 处决只有击中希特勒时公开终局原因

### 14.8 否决权

#### 目标

在后期解锁特殊流程时，仍维持清晰的阶段控制。

#### 功能要求

- 第 `5` 张法西斯政策后，后续立法阶段才允许总理发起否决
- 总理发起否决后，必须等待总统响应
- 同意否决后推进选举轨并检查三连败逻辑
- 拒绝否决后，总理必须继续立法

### 14.9 结果与复盘

#### 目标

让玩家在终局后快速理解“为什么赢 / 输”和关键转折点。

#### 功能要求

- 展示胜利阵营
- 展示胜利原因
- 展示所有玩家最终身份
- 展示关键事件时间线
- 展示每轮当选政府、立法结果、执行权力摘要

#### 保留策略

- 结果页仅面向本局玩家
- 房间失效后，玩家不再能重新访问该局复盘

### 14.10 新手提示与规则说明

#### 目标

降低新玩家接触门槛，但不干扰老玩家节奏。

#### 功能要求

- 每个阶段显示一句话提示“现在要做什么”
- 对被禁操作给出规则原因
- 提供轻量名词解释入口
- 允许在房间内查看简化版规则摘要

## 16. 命令模型与操作矩阵

为方便后续技术方案设计，产品层面先定义关键操作的“谁发起、系统校验什么、公开什么”。

| 命令 | 发起人 | 系统强校验 | 对外公开结果 |
| --- | --- | --- | --- |
| 创建房间 | 任意用户 | 是否已有活跃房间限制、目标人数是否合法 | 房间创建成功 |
| 加入房间 | 任意用户 | 房间是否存在、是否未开局、是否未满 | 玩家加入成功 |
| 准备 | 各玩家 | 是否已在房间中 | 玩家已准备 |
| 开始游戏 | 房主 | 人数是否合法、是否全员准备 | 游戏开始 |
| 提名总理 | 当前总统候选人 | 阶段、目标是否存活、是否符合任期限制 | 总理候选人已确定 |
| 提交投票 | 存活玩家 | 阶段、是否重复提交 | 待全部完成后一次性公开 |
| 总统弃牌 | 当前总统 | 阶段、是否正持有 3 张牌 | 不公开弃牌内容 |
| 总理立法 | 当前总理 | 阶段、是否正持有 2 张牌 | 公布颁布政策 |
| 发起否决 | 当前总理 | 是否已解锁否决权 | 进入总统响应阶段 |
| 响应否决 | 当前总统 | 是否处于否决响应阶段 | 公布接受 / 拒绝结果 |
| 调查忠诚 | 当前总统 | 目标是否合法、是否已被调查过 | 公布调查目标，不公布结果 |
| 特别选举 | 当前总统 | 目标是否合法且不是自己 | 公布下轮临时总统 |
| 预览政策 | 当前总统 | 当前阶段是否合法 | 不公开牌面，仅记录事件 |
| 处决玩家 | 当前总统 | 目标是否存活，允许总统选择自己 | 公布出局对象；若击中希特勒则终局 |

## 17. 异常场景与容错要求

### 17.1 玩家断线或切后台

要求：

- 保留玩家座位与身份绑定
- 玩家重新进入后自动恢复自己的房间和当前视图
- 若玩家在需要操作时离线，房间应保持当前阶段，不得自动越过关键私密动作

### 17.2 重复提交

要求：

- 所有关键命令必须支持幂等保护
- 重复点击提交按钮不能造成重复结算

### 17.3 房主离开

要求：

- 房主退出后，房主身份自动转移给另一位仍在房间内的玩家
- 当所有玩家都退出房间后，房间自动销毁或标记为失效
- 开局后游戏不应依赖房主持续在线

### 17.4 非法操作

要求：

- 非当前行动人不能发起关键命令
- 非法目标、非法阶段、重复操作都必须被系统拒绝
- 拒绝时需要返回用户可理解的提示

### 17.5 小程序分享带回

要求：

- 用户通过分享卡片重新进入时，应优先尝试恢复已有身份座位
- 分享链接只作为“进入房间入口”，不应成为权限凭证

## 18. 对技术架构的输入要求

本节不是技术方案，但它明确规定了架构设计必须满足的产品约束。

### 18.1 必须存在单一可信状态源

游戏不能依赖多个客户端相互推导状态。  
后续架构必须有单一可信状态源负责：

- 规则校验
- 状态推进
- 私密信息裁剪
- 胜负判定

### 18.2 必须区分公开快照与私密快照

后续数据设计至少应能表达三类视图：

- 房间公共快照
- 玩家个人私密快照
- 系统内部完整状态

禁止把完整状态同步给所有客户端后再在前端做隐藏。

### 18.3 必须采用命令驱动，而不是页面驱动

前端应提交“命令”，由系统判断是否生效。  
不能因为某个页面点了按钮，就默认状态一定已经推进。

### 18.4 必须支持事件化记录

为了支持复盘、重连、排障和测试，后续架构应能记录关键事件，而不只是保存最终快照。

建议至少记录：

- 谁在什么时间发起了什么合法操作
- 该操作造成了什么公开结果
- 当前阶段如何切换
- 终局原因是什么

### 18.5 必须支持私密信息的最小暴露

后续技术实现中，以下内容必须限制传播范围：

- 角色信息
- 政策牌内容
- 调查结果
- 预览结果
- 尚未公开的投票

### 18.6 必须支持断线恢复

后续技术设计必须能根据玩家身份标识恢复：

- 所属房间
- 对应座位
- 当前存活状态
- 当前应见页面和待办动作

### 18.7 必须支持阶段级并发控制

虽然一局只有少量玩家，但多个玩家会同时操作，例如投票。  
后续架构必须能处理：

- 多人同时提交
- 阶段结束瞬间的重复请求
- 同一玩家多次点击

### 18.8 必须支持自动过期与清理

由于产品不要求长期留存历史局，后续架构需要支持：

- 空房间自动失效
- 已结束房间自动归档或删除
- 私密中间数据随房间失效而清理

### 18.9 必须便于做自动化测试

后续状态机与规则引擎应能被独立测试，至少要方便验证：

- 每种人数配置
- 每种总统权力触发条件
- 三连败逻辑
- 否决逻辑
- 希特勒当选即时胜负判定
- 处决与剩余人数变化后的任期限制

## 19. 建议核心业务对象

本节用于约束后续领域建模，不代表最终数据库表结构。

| 对象 | 关键字段建议 |
| --- | --- |
| `Room` | 房间号、状态、房主、创建时间、过期时间 |
| `Player` | 玩家标识、展示名、头像、座位号、是否存活、是否在线、是否准备 |
| `Game` | 当前阶段、当前轮次、政策轨、选举轨、当前候选人、任期限制、胜负结果 |
| `RoleAssignment` | 玩家角色、党派、可见队友集合 |
| `PolicyState` | 牌库、弃牌堆、当前立法临时牌组 |
| `ActionTask` | 当前待办动作、操作者、可选目标、截止条件 |
| `GameEvent` | 事件类型、操作者、事件时间、公开摘要、私密载荷 |

## 20. 非功能要求

### 20.1 性能

初期版本建议按以下目标设计：

- 单房最多 `10` 名玩家
- 常规操作反馈时间尽量控制在 `1` 秒内
- 公开状态同步尽量控制在 `2` 秒内

### 20.2 一致性

对于关键流程，一致性优先于弱实时展示。

尤其是：

- 投票结算
- 立法阶段
- 总统权力
- 胜负判定

### 20.3 安全与隐私

- 房号不能作为查看私密信息的唯一凭证
- 房间分享路径中不得携带角色等敏感参数
- 客户端本地缓存中不应长期保留高敏感信息

### 20.4 可用性

- 界面文字要足够大，适应线下快速查看
- 关键按钮应避免误触
- 阶段提示应尽量短、明确、可一扫而知

## 21. 验收标准

产品达到以下条件，可视为满足 MVP：

- `5-10` 人任意标准人数局都能从创建房间完整玩到结算
- 全流程中没有出现角色泄露、越权操作、跳阶段操作
- 玩家切后台后能恢复自己的房间状态
- 新玩家可以在不提前阅读完整规则的前提下，根据提示完成主要操作
- 终局后所有玩家能看到胜负原因与身份公开结果

## 22. 后续技术设计建议的切入顺序

为了降低实现风险，建议后续技术设计按以下顺序展开：

1. 先定义房间、玩家、阶段和事件模型
2. 再定义公开快照与个人私密快照
3. 然后实现规则状态机与命令校验
4. 最后再落页面、同步、异常恢复与复盘展示

如果后续开始写技术方案，建议把 `/docs/game_rules.md` 和本文档一起作为输入，其中：

- `/docs/game_rules.md` 负责定义规则正确性
- 本文档负责定义产品边界、状态拆分和架构约束
