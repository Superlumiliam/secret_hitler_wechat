# 《揭秘希特勒面杀助手》后端职责与技术选型说明

## 1. 文档目标

本文档用于明确《揭秘希特勒面杀助手》后端的职责边界、技术选型建议、领域模块拆分、数据职责与一致性要求。

它将作为后续以下工作的指导输入：

- 云函数设计
- 云数据库建模
- 状态机设计
- 权限控制设计
- 事件日志设计
- 并发控制与异常恢复设计

## 2. 后端定位

后端在本项目中的定位是：

- 单一可信状态源
- 游戏裁判与规则执行者
- 权限与隐藏信息控制者
- 快照投影与同步源
- 事件记录与恢复依据

对本项目而言，后端不是传统“提供几个 CRUD 接口”的服务层，而是整局游戏的可信裁判内核。

## 3. 后端职责边界

## 3.1 后端必须负责的内容

### 3.1.1 用户身份与会话绑定

- 基于小程序云环境识别当前用户
- 把微信身份映射为房间内玩家身份
- 恢复玩家所属房间、座位和在局状态

### 3.1.2 房间生命周期管理

- 创建房间
- 加入房间
- 离开房间
- 房主转移
- 房间过期
- 房间失效清理

### 3.1.3 大厅状态管理

- 玩家列表管理
- 展示名维护
- 准备状态维护
- 座位顺序维护
- 开局条件校验

### 3.1.4 游戏状态机

- 当前阶段推进
- 当前总统候选人与总理候选人
- 任期限制
- 存活状态
- 选举轨
- 政策轨
- 特殊选举状态
- 否决权解锁状态
- 游戏终局状态

### 3.1.5 规则判定

后端必须完整承担 `/docs/game_rules.md` 中与程序实现有关的规则判定，包括但不限于：

- 人数对应身份配置
- 可提名对象校验
- 投票通过 / 失败判定
- 三连败翻牌逻辑
- 希特勒当选即时判定
- 立法流程
- 牌库重洗
- 总统权力触发
- 调查、特别选举、政策预览、处决
- 否决逻辑
- 胜负判定

### 3.1.6 隐藏信息裁剪

后端必须决定：

- 哪些字段属于公共信息
- 哪些字段只对当前玩家可见
- 哪些字段只允许系统内部持有

### 3.1.7 快照投影

后端必须产出至少三类视图：

- 大厅视图
- 游戏公共快照
- 玩家私密快照

### 3.1.8 事件日志

后端必须记录关键事件，用于：

- 复盘
- 重连恢复
- 排障
- 测试
- 并发问题追踪

### 3.1.9 并发与幂等控制

后端必须处理：

- 多名玩家同时投票
- 同一玩家重复点击
- 阶段切换瞬间的旧请求
- 弱网重试导致的重复提交

## 3.2 后端明确不负责的内容

后端不应承担以下职责：

- 具体页面布局
- 小程序动画与交互细节
- 本地按钮展示时机的纯 UI 设计
- 局内说明文案的视觉组织
- 页面滚动、弹层或卡牌翻转表现

后端只负责“什么可以做、发生了什么、谁能看到什么”，不负责“前端具体怎么表现这些信息”。

## 4. 后端技术选型原则

本项目的后端选型必须优先适配微信小程序，而不是优先追求通用互联网后端架构。

## 4.1 推荐技术路线

推荐采用：

- 微信云开发
- 云函数
- 云数据库
- TypeScript 编写后端领域代码
- 命令驱动 + 状态机 + 快照投影

## 4.2 选择该路线的原因

- 与微信小程序身份体系天然兼容
- 无需自建服务器、域名、网关与登录体系
- 对 MVP 阶段的小规模房间协作场景足够
- 能快速承接分享回流、云函数调用和真机调试
- 更利于前后端都围绕微信生态收敛复杂度

## 4.3 当前阶段不推荐的路线

不推荐优先采用：

- 自建传统 HTTP 服务端
- 独立公网数据库
- 跨平台 BFF
- 前端直连第三方后端

原因如下：

- 会显著增加运维、域名、审查和安全配置成本
- 会削弱微信云身份的天然优势
- 对当前房间型桌游 MVP 来说收益不高

## 5. 后端最优技术选型建议

## 5.1 运行环境

### 结论

采用微信云开发云函数作为主执行环境。

### 原则

- 房间管理逻辑运行在云函数
- 游戏命令处理运行在云函数
- 快照生成与写入运行在云函数

### 说明

如果后续遇到明显的资源、执行时长或复杂依赖限制，再评估迁移到云托管；但当前版本不作为默认方案。

## 5.2 开发语言

### 结论

采用 TypeScript 编写后端业务逻辑，再编译部署到云函数。

### 原则

- 核心领域类型必须强类型定义
- 状态机输入 / 输出必须类型化
- 命令与事件必须类型化

## 5.3 数据存储

### 结论

采用云数据库作为主存储。

### 原则

- 核心状态存储在可信集合中
- 公共快照与私密快照分开存储
- 事件日志独立存储
- 前端不可直接写核心集合

## 5.4 后端架构模式

### 结论

采用“命令处理器 + 状态机 + 投影器 + 仓储”的分层模式。

### 推荐分层

- `handlers`：云函数入口与 action 分发
- `application`：命令处理与事务编排
- `domain`：规则模型、状态机、判定逻辑
- `repositories`：数据库读写封装
- `projectors`：公共 / 私密快照生成
- `events`：事件定义与记录

## 6. 后端领域模块建议

## 6.1 身份与会话模块

负责：

- 获取当前小程序用户身份
- 建立玩家与房间成员映射
- 处理重进恢复

不负责：

- 自定义账号密码体系

## 6.2 房间模块

负责：

- 房间创建
- 房间号生成
- 房间加入 / 退出
- 房主转移
- 座位调整
- 准备状态
- 开局前校验

## 6.3 游戏模块

负责：

- 开局初始化
- 角色分配
- 总统轮换
- 选举阶段
- 立法阶段
- 总统权力
- 胜负判定

## 6.4 快照投影模块

负责：

- 生成大厅视图
- 生成公共桌面快照
- 生成个人私密快照
- 维护待办任务视图

## 6.5 事件日志模块

负责：

- 记录命令接受与应用结果
- 记录阶段切换
- 记录终局原因
- 支撑复盘视图

## 6.6 清理与保活模块

负责：

- 空房间清理
- 已结束房间过期
- 私密临时数据清理
- 长时间未活动房间失效

## 7. 数据职责划分建议

建议至少区分以下几类数据对象：

| 对象 | 作用 |
| --- | --- |
| `rooms` | 房间基础信息、状态、房主、过期时间 |
| `room_members` | 玩家与房间成员映射、座位、准备、在线状态 |
| `game_core` | 完整可信游戏状态 |
| `room_public_snapshots` | 所有成员可消费的公共快照 |
| `player_private_snapshots` | 仅对应玩家可消费的私密快照 |
| `game_events` | 事件流与复盘数据 |
| `command_records` | 命令幂等与请求记录 |

这些名称是推荐的领域对象边界，不强制等同于最终数据库表名，但不应把它们混成一个“大 JSON 文档”。

## 8. 一致性与并发要求

## 8.1 单一可信状态源

必须只有一个可信游戏真相来源，即：

- 房间核心状态只以后端持久化状态为准
- 前端本地状态只是缓存和渲染辅助

## 8.2 命令串行化原则

虽然房间中有多人同时操作，但最终状态更新必须按命令结果线性化。

尤其是：

- 投票阶段
- 阶段切换瞬间
- 立法阶段
- 否决响应

## 8.3 幂等要求

每个命令都必须支持幂等保护，至少要基于：

- `commandId`
- 当前用户身份
- 当前房间
- 当前阶段版本

进行识别。

## 8.4 版本要求

核心状态应维护显式版本号或等价机制，用于：

- 防止旧快照上的过期操作覆盖新状态
- 协助前端提示“状态已更新，请刷新”

## 9. 安全与权限要求

## 9.1 权限控制原则

- 房主不拥有额外秘密查看权
- 房号不等于权限
- 所有关键操作以后端上下文识别操作者
- 所有快照都按“谁可见”投影后再暴露

## 9.2 数据暴露原则

以下信息不得直接暴露给前端公共视图：

- 完整角色映射
- 牌库顺序
- 弃牌堆内容
- 他人的隐藏手牌
- 他人的调查结果
- 未揭示投票中间态

## 9.3 集合访问原则

- 核心集合禁止前端直接写
- 内部真相集合禁止前端直接读
- 可被前端订阅的集合必须是已裁剪好的视图集合

## 10. 可测试性要求

后端设计必须便于做自动化测试。

至少应支持：

- 纯规则单元测试
- 状态机流转测试
- 各人数开局配置测试
- 命令处理集成测试
- 终局与异常场景测试

不应把关键规则散落在多个云函数入口文件中，否则后续测试和排障成本会非常高。

## 11. 观测与排障要求

后端必须至少提供以下排障能力：

- 命令请求日志
- 状态版本日志
- 阶段切换日志
- 终局日志
- 失败错误码

日志的目标不是做大而全监控，而是保证在“这局为什么卡住了”“为什么重复结算了”这类问题出现时可以快速定位。

## 12. 后端不建议采用的方案

- 不建议用前端直写数据库代替命令处理
- 不建议把所有逻辑塞进一个超大云函数文件
- 不建议将完整状态文档直接透传给前端
- 不建议只保存最终快照、不保存事件
- 不建议把规则判定混写在数据库读写代码里

## 13. 交付给后续后端技术设计的结论

后续后端技术细节设计应以以下结论为前提：

- 采用微信云开发云函数 + 云数据库
- 采用 TypeScript 编写领域逻辑
- 采用“命令处理 + 状态机 + 快照投影 + 事件日志”的核心架构
- 由后端独占规则判定、权限裁剪和终局决定权
- 前端只消费后端定义的公共 / 私密快照与命令 API
