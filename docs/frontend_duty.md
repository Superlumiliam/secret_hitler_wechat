# 《揭秘希特勒面杀助手》前端职责与技术选型说明

## 1. 文档目标

本文档用于明确《揭秘希特勒面杀助手》微信小程序前端的职责边界、技术选型原则、模块拆分建议与实现约束。

它的定位不是详细开发手册，而是后续前端技术细节设计、页面拆分、组件设计和联调实现的上位指导。

本文档与其他文档的关系如下：

- `/docs/secret_hitler_prd.md`：定义产品目标、范围和状态约束
- `/docs/game_rules.md`：定义规则正确性
- `/docs/front_back_api.md`：定义前后端交互约束

## 2. 前端定位

前端在本项目中的定位是：

- 小程序原生交互承载层
- 玩家视图呈现层
- 用户操作采集层
- 本地轻状态管理层

前端不是裁判，不负责判定规则对错，不负责维护完整对局真相。

换句话说，前端负责“展示当前该玩家应该看到什么”和“把该玩家的合法意图提交给后端”，而不是负责“推演下一步会发生什么”。

## 3. 前端职责边界

## 3.1 前端必须负责的内容

### 3.1.1 小程序壳能力

- 小程序启动初始化
- 云开发 SDK 初始化
- 分享入口与分享文案
- 页面路由与页面栈管理
- `onShow` / `onHide` / `onUnload` 等生命周期处理

### 3.1.2 页面与组件展示

- 房间大厅页
- 身份查看页
- 公共桌面页
- 私密操作页或弹层
- 结果复盘页
- 局内规则说明入口

### 3.1.3 玩家交互采集

- 创建房间
- 输入房号加入
- 修改展示名
- 准备 / 取消准备
- 调整座位顺序
- 投票
- 总统弃牌
- 总理立法
- 发起 / 响应否决
- 调查忠诚
- 特别选举
- 处决

### 3.1.4 本地 UI 状态

- 当前页面 loading 状态
- 按钮禁用态
- 弹层显示状态
- 私密卡牌遮罩显示状态
- 局内提示文案的展开 / 收起
- 提交中的幂等保护

### 3.1.5 视图同步

- 获取大厅快照和游戏快照
- 订阅公共快照与个人私密快照变更
- 切后台返回后的视图恢复
- 命令提交后的局部刷新或全量刷新

### 3.1.6 轻量规则提示

前端可以做“提示型校验”，例如：

- 当前按钮置灰
- 不可提名玩家显示原因
- 非当前行动人不显示操作按钮

但这些只属于用户体验增强，不属于可信规则判断。

## 3.2 前端明确不负责的内容

前端不得承担以下职责：

- 角色分配
- 政策牌洗牌与发牌
- 胜负判定
- 任期限制计算
- 各阶段合法性最终判定
- 总统权力触发判断
- 隐藏信息可见性最终裁剪
- 重复命令去重的最终判定
- 房间核心状态的直接持久化写入

一句话约束：

前端可以“猜测界面怎么表现更合理”，但不能“决定游戏状态是什么”。

## 4. 技术选型原则

本项目是微信小程序单平台产品，因此前端技术选型必须优先服从微信生态，而不是跨端便利性。

## 4.1 推荐技术路线

推荐采用：

- 原生微信小程序框架
- TypeScript
- 原生 `Page` + `Component` 组件化
- `wx.cloud` 官方云开发 SDK
- 小程序原生分包能力
- 轻量自定义状态管理

## 4.2 不推荐技术路线

当前阶段不推荐：

- Taro
- uni-app
- 自建 WebView 容器式方案
- 复杂跨端状态框架优先驱动页面开发

原因如下：

- 当前产品没有多端复用诉求
- 项目深度依赖小程序生命周期与分享能力
- 原生小程序在真机调试、审核适配和云开发接入上成本最低
- 跨端抽象会削弱对平台细节的控制，尤其不利于私密信息显示和页面恢复

## 5. 前端最优技术选型建议

## 5.1 框架层

### 结论

使用原生微信小程序框架，不引入跨端框架。

### 理由

- 页面能力、分享能力、生命周期和云开发接入最直接
- 更贴合微信开发者工具调试模式
- 对性能、首包、分包和审核限制的感知更清晰
- 更适合细颗粒度控制私密界面与前后台切换行为

## 5.2 语言层

### 结论

使用 TypeScript 作为前端主语言。

### 理由

- 游戏阶段、命令类型、快照结构、任务结构都适合强类型建模
- 可降低前后端联调时字段误用风险
- 便于维护枚举、联合类型和领域对象映射

### 要求

- 所有 API 请求和响应都必须定义类型
- 所有核心领域枚举必须显式声明
- 不允许在业务层散落无类型字符串常量

## 5.3 样式与 UI

### 结论

使用原生 WXSS 与小程序组件能力实现界面。

### 理由

- 当前产品交互强于视觉炫技
- 小程序 WXSS 已足够承载房间页、桌面页、卡牌与状态提示
- 避免为引入样式系统增加额外构建复杂度

### 要求

- 重点保证状态清晰、按钮明确、字号足够
- 私密信息与公共信息要形成明显视觉区隔
- 不使用会弱化状态表达的复杂炫目动效

## 5.4 状态管理

### 结论

采用“页面局部状态 + 应用级轻量 store”的方案，不优先引入重型状态管理框架。

### 推荐分层

- 页面 `data`：只负责该页即时渲染状态
- `app` 级 session store：保存用户会话、房间上下文、当前玩家身份摘要
- `services`：封装所有云函数调用和快照拉取
- `view-model` / `mapper`：把后端快照映射成页面可直接使用的结构

### 原则

- 页面不直接拼接后端原始字段做复杂逻辑
- 页面不直接维护完整游戏状态副本
- 所有跨页共享状态都要经过明确封装

## 5.5 联机与同步

### 结论

优先采用“快照订阅 + 命令调用”的模式。

### 推荐做法

- 所有写操作通过 `wx.cloud.callFunction`
- 公共快照和个人私密快照通过后端投影提供
- 前端优先订阅可安全监听的快照集合
- 若监听稳定性或权限控制不足，则降级为定时拉取

### 原则

- 写请求和读视图严格分离
- 页面渲染只依赖快照，不依赖本地猜测
- 命令提交后，以服务端返回或新快照为准更新 UI

## 5.6 分包策略

### 结论

应使用小程序分包能力，减轻首包压力。

### 推荐分包方式

- 主包：启动页、首页、创建房间、加入房间
- 分包一：大厅与局内流程页
- 分包二：结果复盘与规则说明页

### 原则

- 首屏相关资源尽量留在主包
- 局内复杂页面和复盘页放入分包
- 共享组件放在主包公共目录或公共组件目录

## 6. 前端模块划分建议

## 6.1 页面层

建议至少包含以下页面：

- `pages/home`
- `pages/room-lobby`
- `pages/game-board`
- `pages/identity`
- `pages/result`
- `pages/rules`

## 6.2 组件层

建议抽离以下高复用组件：

- 玩家座位组件
- 阶段提示组件
- 政策轨组件
- 选举轨组件
- 投票面板组件
- 私密卡牌组件
- 操作任务卡组件
- 错误提示 / 空态组件

## 6.3 服务层

前端服务层建议包含：

- `sessionService`
- `roomService`
- `gameService`
- `snapshotService`
- `shareService`

这些服务只负责：

- 调 API
- 做响应解析
- 管理本地请求状态

这些服务不负责：

- 本地复刻规则引擎
- 维护对局真相

## 6.4 类型层

建议建立统一的 `types` 目录，至少包含：

- 房间相关类型
- 玩家相关类型
- 快照类型
- 命令类型
- 错误码类型
- UI 任务类型

## 6.5 工具层

建议抽出以下工具能力：

- 防抖 / 幂等点击工具
- 时间与倒计时工具
- 字段映射工具
- 日志与埋点工具
- 页面恢复工具

## 7. 页面数据原则

## 7.1 前端页面必须消费“视图快照”

页面渲染应直接面向：

- 大厅快照
- 游戏公共快照
- 当前玩家私密快照
- 当前待办任务

而不是面向后端内部数据库模型。

## 7.2 前端不得持有完整真相

前端不应收到以下内容：

- 全量角色映射
- 牌库顺序
- 弃牌堆完整内容
- 他人未公开投票
- 他人政策手牌
- 他人调查结果

## 7.3 当前待办必须由后端下发

前端页面不应靠本地推理决定“现在轮到谁操作”，而应依据后端返回的：

- `currentPhase`
- `pendingTask`
- `allowedActions`

进行界面渲染。

## 8. 前端交互约束

## 8.1 命令驱动

所有会改变游戏状态的前端交互都必须转化为命令提交给后端，例如：

- 提名某玩家
- 提交投票
- 弃掉某张牌
- 发起否决
- 指定特别选举目标
- 处决某玩家

前端不得直接对核心集合执行写操作。

## 8.2 提交幂等

所有关键按钮都必须具备以下能力：

- 点击后立即进入提交中状态
- 重复点击不会重复提交
- 提交成功前不能再次触发同一命令
- 提交失败后可重新尝试

## 8.3 弱网恢复

前端必须考虑以下场景：

- 用户切后台
- 微信会话跳转回来
- 网络短时不可用
- 云函数调用超时

前端需要提供：

- 明确的等待反馈
- 刷新重试入口
- 恢复当前房间与当前快照的能力

## 9. 隐私与安全要求

## 9.1 私密信息展示约束

- 身份卡默认遮罩
- 策略牌默认遮罩
- 调查结果默认只在对应玩家界面中展示
- `onHide` 后可回到安全态
- 不将高敏字段长期存入本地缓存

## 9.2 数据边界约束

- 不直接读取后端内部真相集合
- 不允许前端基于 roomCode 推断权限
- 不信任本地 memberId、seatIndex、roleName 作为最终可信依据

## 10. 性能要求

前端设计应遵守以下要求：

- 首屏尽快进入创建 / 加入房间入口
- 局内页面切换不做重型动画
- 公共桌面优先可读性，其次才是视觉装饰
- 低频复杂视图放入分包
- 图片和静态资源总量保持克制

## 11. 前端不建议采用的方案

- 不建议在前端实现规则状态机
- 不建议将多个页面都维护一份完整 room/game 对象副本
- 不建议直接从前端写入核心对局集合
- 不建议基于 Web 思维套用大型 SPA 架构
- 不建议引入过多第三方 UI 依赖

## 12. 交付给后续前端技术设计的结论

前端后续技术细节设计应以以下结论为前提：

- 采用原生微信小程序 + TypeScript
- 采用原生页面与组件化，不采用跨端框架
- 采用“快照渲染 + 命令提交”的交互模型
- 采用轻量状态管理，不实现前端裁判逻辑
- 所有游戏真相、规则校验和权限判断都以后端为准
