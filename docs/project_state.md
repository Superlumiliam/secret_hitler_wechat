## Development Todo

以下待办按线下面杀玩家完成一整局游戏的真实流程拆分。每个功能都应同时考虑“线下玩家正在做什么”“小程序需要展示什么”“后端必须强校验什么”。  
P0 目标是让 `5-10` 人可以不依赖主持人完成一整局标准《secret dictator》/《揭秘独裁者》。

### P0-01 本地用户资料与创建/加入前置流程

[x] 创建用户页完整功能

- 前端实现 `pages/user-profile`：支持首次创建头像与用户名、后续修改、保存成功后回到原入口流程。
- 用户名需做长度、空值、敏感空白字符校验；头像选择需有默认头像兜底。
- 保存后本地缓存用户资料，并在创建房间、加入房间前自动校验资料是否存在。
- 创建 / 加入房间时继续沿用房间临时头像上传策略，保证房间过期后可被 `maintenanceService` 清理。
- 页面视觉保持铜色档案风，整页使用宋/明体气质字体栈，避免和首页、创建房间页风格割裂。

[x] 首页进入路径串联

- 首页“创建房间”点击后：若无本地用户资料，先跳转创建用户页；若已有资料，进入创建房间页。
- 首页“加入房间”点击后：若无本地用户资料，先跳转创建用户页；若已有资料，允许输入房号或处理分享卡片参数。
- 首页“单人模式”点击后：若无本地用户资料，先跳转创建用户页；若已有资料，进入创建房间页选择人数，不在首页直接选择人数。
- 完成用户资料后，需要能回到原本意图：创建房间、加入房间、单人模式或恢复活跃房间。
- 补齐 `bootstrapService.ensureSession` 与 `recoverActiveRoom` 的前端调用包装，应用启动时判断是否应进入大厅、对局桌面或结果页。

### P0-02 创建房间与大厅等待

[x] 创建房间页完整功能

- 前端实现 `pages/create-room`：选择 `5-10` 人局，展示不同人数对应的阵营配置概要。

- 创建成功后进入大厅页，并展示房号、目标人数、当前人数、分享入口。
- 处理创建失败、房间码冲突重试失败、网络异常等错误码映射。

[x] 加入房间完整功能

- 加入前校验房号格式；加入后进入大厅页并读取 `LobbyView`。
- 后端需拦截房间不存在、房间已过期、房间已满、游戏已开始、重复加入等场景。

[x] 大厅页完整功能

- 房主可在人数满足且全员准备后点击开始游戏，调用 `gameService.startGame`。

- 大厅通过 `getLobbySnapshot` 轮询刷新，命令成功后立即补拉一次，不能只依赖本地按钮状态。
- 处理玩家退出、房主退出后的房主转移、房间过期、重复点击、版本更新后的 UI 回显。

[x] 大厅房间设置功能

- 房主可从大厅进入创建房间页的房间设置模式，调整当前房间席位数量。
- 该能力不重建房间、不改变房间号、不触发房主离开或房主转移，已落座玩家席位保持不变。
- 已实现 `roomService.updateRoomSettings`，只允许大厅房主调用，选择人数小于已落座玩家数时返回 `TARGET_COUNT_BELOW_SEATED`。
- 已补充后端隔离测试，覆盖房主成功调整、非房主拒绝、选择人数小于已落座玩家数拒绝。

### P0-03 开局发牌与身份页

[x] 后端开局初始化

- `gameService.startGame` 需要在事务内完成：锁定房间状态、校验人数与准备状态、按人数分配角色、生成党派归属、洗混政策牌库、随机首位总统候选人、创建 `game_core`、写入初始事件日志。
- 根据人数配置生成自由派、普通极权派、独裁者数量；普通极权派始终知道队友和独裁者，独裁者仅在 `5-6` 人局知道普通极权派。
- 初始化政策牌库为 `6` 张自由派政策与 `11` 张极权派政策，弃牌堆为空。
- 初始化公共快照与每位玩家私密快照，前端不得拿到完整真相。

[x] 身份页完整功能

- 前端实现 `packageRoom/pages/identity`：展示当前玩家自己的身份、党派、阵营说明和开局可见队友信息。

- 身份页从 `gameService.getGameSnapshot` 的当前玩家私密快照读取，不做本地推断。
- 身份信息展示后提供“返回对局桌面”入口；局内也可随时从桌面入口或自己的席位头像进入身份页查看自己的身份。
- 身份页不得展示其他玩家无权限可见的信息，不设计房主查看全部身份能力。

### P0-05 提名阶段 `nomination`

[x] 总理提名命令

- 当前总统候选人的私密任务中展示可提名玩家列表，其他玩家只看到“等待总统候选人提名”。
- 可提名列表由后端基于规则生成，前端只负责展示，不自行判断最终资格。
- 后端实现 `submitCommand` 命令：提名总理候选人，校验操作者是否为当前总统候选人、目标是否存活、目标不是自己、目标符合任期限制。
- 任期限制只看上一届成功当选政府；提名失败的组合不进入任期限制。
- 当存活玩家只剩 `5` 人时，上一届总统可被提名为总理，上一届总理仍不可被提名。
- 提名成功后进入 `voting` 阶段，公共快照展示总统候选人与总理候选人。

[x] 提名阶段 UI 席位化改造

- 桌面页突出当前总统候选人和可选总理候选人。
- 移除当前独立提名面板，改为总统候选人点击玩家席位选择目标，再点击底部“提名”按钮。
- 可提名玩家点击“提名”后弹出确认弹框，确认后才提交 `NOMINATE_CHANCELLOR`。
- 不可提名玩家也允许被点击查看原因；点击“提名”时弹框提示已出局、不能提名自己、受任期限制影响等具体原因。
- 总统候选人提交后禁用重复提交，若收到 `VERSION_CONFLICT` 立即刷新快照。
- 线下讨论不需要倒计时，MVP 中 `pendingTask.deadline` 保持 `null`。

### P0-06 投票阶段 `voting`

[x] 全员投票命令

- 每名存活玩家收到投票任务，可选择 `JA` 或 `NEIN`。
- 候选总统和候选总理也必须投票；已出局玩家不可投票。
- 后端记录每名玩家投票，但在全部存活玩家投票完成前不向公共快照泄露单人票。
- 全部投票完成后公开每位玩家票型、赞成票数、反对票数和政府是否通过。
- 赞成票严格超过存活玩家半数才通过，平票视为不通过。

[x] 投票失败结算

- 政府未通过时，选举计数器 `+1`，总统候选人顺时针轮换到下一名存活玩家。
- 若选举计数器未达到 `3`，进入下一轮 `nomination`。
- 若选举计数器达到 `3`，触发混乱政策：后端翻开牌库顶牌直接颁布、忽略该政策对应总统权力、重置选举计数器、清空当前总理任期限制。
- 混乱政策也要触发自由派 `5` 张或极权派 `6` 张的胜负判定。
- 牌库不足时先按规则将剩余牌库与弃牌堆重洗，再翻开顶牌。

[x] 投票通过结算

- 政府通过时，当前总统候选人成为正式总统，总理候选人成为正式总理。
- 若当前极权派政策数已达到 `3+`，后端立即检查新总理是否为独裁者。
- 若新总理是独裁者，极权派立即胜利并进入 `game_ended`。
- 若新总理不是独裁者，公共快照可提示“该总理已通过危险阶段检查”，随后进入 `legislative_president`。
- 政府通过后更新上一届当选政府，用于下一轮总理提名限制。

[x] 投票阶段 UI

- 每名玩家手机上展示自己的投票按钮；已投票后显示等待其他玩家。
- 公共桌面展示投票进度，例如“已投票 4/7”，但不提前展示具体票型。
- 结算后展示公开投票表、是否通过、选举计数器变化和下一阶段提示。
- 对 `3+` 极权派政策后的政府通过结果，需要有明显危险阶段反馈。

### P0-07 总统立法阶段 `legislative_president`

[x] 总统弃牌命令

- 政府通过且未触发即时胜负后，总统私密收到 `3` 张政策牌。
- 后端从牌库顶抽 `3` 张，生成本轮临时立法上下文，只在总统私密快照中展示。
- 总统选择弃掉 `1` 张，调用 `submitCommand`；后端校验操作者、阶段、牌 ID、重复提交。
- 弃掉的牌进入弃牌堆，剩余 `2` 张进入总理立法上下文。
- 其他玩家公共桌面只显示“总统正在处理政策牌”，不展示牌面。

[x] 总统立法 UI

- `policy-picker` 组件支持展示三张政策牌和“弃掉此牌”动作。
- 提交前二次确认，文案强调“弃牌不会公开，事后可自由陈述”。
- 提交后进入等待状态，直到服务端快照进入 `legislative_chancellor`。
- 禁止使用随机选择等弱化玩家决策的 UI。

### P0-08 总理立法阶段 `legislative_chancellor`

[x] 总理颁布命令

- 总理私密收到总统留下的 `2` 张政策牌。
- 总理选择颁布 `1` 张，另一张进入弃牌堆。
- 后端校验操作者、阶段、牌 ID、是否来自当前总理可见的两张牌。
- 颁布政策后更新自由派或极权派政策轨，任意正面颁布政策都重置选举计数器。
- 颁布后先检查自由派 `5` 张或极权派 `6` 张胜利条件。
- 若未结束且本次颁布的是带总统权力的极权派政策，进入 `executive_action`；否则进入下一轮 `nomination`。
- 立法结束后若牌库剩余不足 `3` 张，按规则重洗牌库与弃牌堆。

[x] 总理立法 UI

- `policy-picker` 组件支持两张政策牌和“颁布此牌”动作。
- 其他玩家公共桌面显示“总理正在处理政策牌”，不展示牌面。
- 颁布后公共桌面播放或突出新增政策格，随后展示是否触发总统权力或胜负。
- 立法结果只公开最终颁布政策，不公开总统和总理弃掉的牌。

### P0-09 执行阶段与总统权力 `executive_action`

[x] 总统权力配置与触发

- 后端根据玩家人数和当前极权派政策数量配置权力：调查忠诚、特别选举、政策预览、处决。
- 混乱政策颁布时即使落在权力格，也必须忽略总统权力。
- 第 `5` 张极权派政策颁布后，仍先触发处决；否决权只从后续立法阶段开始解锁。
- 执行权力必须完成后才能进入下一轮。

[x] 调查忠诚

- 总统选择一名未被调查过的其他存活玩家，不能调查自身；若总统点击自身，前端弹框提示“不能调查自身”。
- 后端返回给总统的私密结果只包含党派归属：自由派或极权派；不能暴露普通极权派与独裁者的区别。
- 后端在当前总统的私密快照中维护 `investigationMarks`，供前端在目标席位右上角展示仅自己可见的调查印章。
- 同一玩家整局不能被重复调查。
- 公共事件只记录“总统调查了某玩家”，不公开调查结果。
- 总统之后在线下可以说真话或说谎，小程序不验证发言。

[x] 特别选举

- 总统选择任意另一名存活玩家作为下一轮特别总统候选人。
- 后端记录 `specialElectionCallerId` 与 `forcedNextPresidentId`，下一轮先由指定玩家担任总统候选人。
- 特别选举结束后，总统轮换回到发动特别选举总统的左手边继续。
- 公共快照需要明确展示下一任特别总统候选人，避免线下误解顺序。

[x] 政策预览

- 总统私密查看牌库顶 `3` 张政策牌。
- 后端不得改变牌库顺序，也不得把预览结果写入公共快照。
- 总统确认看完后，进入下一轮 `nomination`。
- 公共事件只记录“总统查看了牌库顶端政策”，不公开牌面。

[x] 处决

- 总统选择一名存活玩家处决，规则允许选择自己。
- 被处决玩家立即出局，后续不能投票、被提名、成为总统候选人或执行动作。
- 如果被处决者是独裁者，自由派立即胜利并进入 `game_ended`。
- 如果被处决者不是独裁者，不公开其阵营或身份，只公开出局事实。
- 处决后如果游戏未结束，进入下一轮 `nomination`。

[x] 执行阶段 UI

- `target-picker` 组件根据权力类型展示合法目标和不可选原因。
- `secret-panel` 组件用于调查结果和政策预览结果，只在当前总统私密任务中展示。
- 公共桌面展示“总统正在执行权力”，完成后写入公开事件。
- 各权力需要有明确完成按钮，避免玩家看完私密信息后停留在阶段内。

### P0-10 否决权 `veto_response`

[x] 否决权解锁与总理发起

- 当第 `5` 张极权派政策已经颁布后，从后续立法阶段开始，总理在收到 `2` 张政策牌时可选择“提出否决”。
- 总理也可以不提出否决，直接选择颁布 `1` 张政策。
- 后端校验否决权是否已解锁、当前阶段是否允许、操作者是否为当前总理。

[x] 总统响应否决

- 总理提出否决后进入 `veto_response`，总统收到“同意否决 / 拒绝否决”任务。
- 总统同意时，本轮两张政策全部弃掉，不颁布政策，选举计数器 `+1`。
- 总统拒绝时，回到总理必须从两张政策中选择 `1` 张颁布。
- 成功否决不会清空任期限制，因为本轮政府已经当选。
- 若成功否决导致选举计数器达到 `3`，触发混乱政策流程。

[x] 否决权 UI

- 总理立法界面在否决权解锁后展示“提出否决”入口，同时保留正常颁布入口。
- 总统响应界面清晰展示总理提出了否决请求，并说明同意后本轮不颁布政策但选举计数器推进。
- 公共桌面展示否决请求正在等待总统响应，不展示总理手牌。
- 否决结算后公开记录总统是否同意、选举计数器变化和后续阶段。

### P0-13 断线恢复、轮询与异常处理

[x] 前端恢复机制

- 应用启动、页面显示、从后台回到前台时调用 `recoverActiveRoom`。
- 根据 `routeHint` 自动跳转到大厅、对局桌面或结果页。
- 对局页和大厅页恢复后立即拉取最新快照，避免继续展示旧阶段按钮。
- 本地只缓存会话入口信息，不缓存角色真相、政策牌真相或完整游戏状态。

[x] 命令幂等与版本冲突处理

- 所有写操作生成并复用 `commandId`，重复点击同一动作不得产生多个逻辑命令。
- 游戏内命令必须携带 `expectedVersion`。
- 收到 `VERSION_CONFLICT` 时立即刷新快照，并提示“局势已更新，请按最新页面操作”。
- 收到 `PHASE_MISMATCH`、`FORBIDDEN`、`ALREADY_ACTED` 等错误时，禁用当前过期操作并刷新。

[x] 实时信号与轮询降级策略

- 大厅与对局页监听只读 `room_sync_signals`，信号只包含房间状态和版本。
- 监听健康时大厅每 `10s`、对局每 `60s` 校准；监听异常时恢复原 `3s` / 动态 `0.8s-4s` 轮询。
- watcher 连接失败或断开时按 `30s`、`60s`、`120s`、`300s` 退避重建，达到最大间隔后每 `300s` 重试；收到有效信号后重置退避序列。
- 页面隐藏时关闭监听并停止轮询，页面显示时立即拉取并重建监听。
- 快照心跳每 `60s` 显式触发并复用已有成员鉴权结果，不再重复查询成员；服务端按成员 ID 与持久化 `lastSeenAt` 截止时间原子更新，并发实例最多一个实际写入。
- 连续同步信号在同一房间状态内记录最高待处理版本，状态变化独立触发快照；进行中快照结束后自动追赶，且不产生并发快照请求。
- 大厅命令成功后的信号刷新在独立事务内重新读取房间并写入，避免延迟的旧大厅投影覆盖并发开局信号。
- 实时同步首次上线前必须先通过 `maintenanceService.prepareRoomSyncSignals` 显式初始化集合，再在微信云开发助手中直接配置并验证集合权限，最后部署信号生产端；仓库代码不负责应用数据库权限。
- 命令成功后立即补拉一次快照，减少线下等待。
- 大厅、对局、结果页及其规则 / 身份 / 历史辅助页需按房间 TTL 做页面超时处理：停止轮询、清理活跃房间恢复锚点、回首页并提示“页面已超时”。
